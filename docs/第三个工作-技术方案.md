# 第三个工作技术方案

## 企业级集装箱门把手盖多智能体协同缺陷检测系统

本文档围绕第三个工作的关键技术决策展开，供审阅系统架构、数据组织与智能体机制使用。业务范围为中国铁路集装箱公司的单企业、多角色、多用户检修场景。系统以深度学习检测算法为计算基础，将检测、复核、后续处理与报告交付组织为企业业务流程，并通过智能体辅助处理跨模块、重复性强的专业任务。

**总体选择：五个领域服务与独立Python推理执行平面，采用Apache Seata协调跨服务事务，配合领域数据所有权、分布式运行保障和受控多智能体协作。** 服务划分依据业务责任，数据库划分依据事务和事实归属，智能体按授权工具参与业务，经验更新采用固定模型参数的记忆驱动适应机制。

八项重点方案如下。

| 技术方案 | 对应问题 | 核心解决办法 |
| --- | --- | --- |
| 1. 服务划分与算法服务化 | 实验程序难以直接供检修人员使用，推理负载影响在线操作 | 领域服务分层、独立推理执行、持久任务与异步消息 |
| 2. 数据库划分与一致性 | 数据重复、修改责任不清，跨服务超时导致重复操作 | 领域私有数据、本地事务、Seata TCC/Saga及短时AT事务、Outbox与幂等回执 |
| 3. 单企业多角色多用户 | 业务需要协作，但职责、数据范围及私人会话不能混同 | 角色授权、资源范围、状态与版本联合校验 |
| 4. 微服务治理与高可用 | 节点故障、网络异常及资源竞争影响业务连续性 | 服务发现、接纳控制、故障隔离、副本复制与执行恢复 |
| 5. AgentScope与中间件集成 | 智能体需要连接业务、模型、记忆和工具运行环境 | 分层适配、统一身份传播、业务事实与派生状态分离 |
| 6. 多智能体协同 | 跨模块任务需要反复查询与人工汇总，独立步骤串行等待 | 角色主智能体、专业委派、依赖约束下的并行调度 |
| 7. SOP复用与上下文管理 | 重复规划增加操作成本，长对话容易遗漏步骤与依据 | 版本化标准作业程序、检查点、上下文分层与来源引用 |
| 8. 反馈反思与经验自进化 | 纠正停留在单次会话，后续任务重复出现相同错误 | 轨迹采集、反馈归因、经验蒸馏、评估发布与检索增强 |

## 1. 服务划分与深度学习算法服务化

### 1.1 按业务事实的修改责任划分服务

实验算法以图像和模型参数为输入，企业人员则围绕任务、责任与质量结论开展工作。系统将界面交互、领域规则和模型计算分层，避免让人员直接操作权重、脚本和运行环境，也避免把推理过程放入同步业务请求。

| 运行单元 | 独占管理的业务事实 | 主要协作方式 |
| --- | --- | --- |
| 资源服务 | 账号、员工、部门、设备及其使用关系 | 提供当前人员身份、组织关系和资源授权依据 |
| 模型服务 | 视觉模型、权重版本、部署清单和使用引用 | 提供模型准入、制品核验与回收约束 |
| 检测服务 | 图片组织、检测任务、调度、复核及复核结果处理 | 派发推理、接收结果、维护检修状态机 |
| 报告服务 | 报告草稿、审批快照和冻结交付记录 | 核验检测事实，执行独立审批与多格式交付 |
| 智能体服务 | 会话、专业委派、工具调用、工作区与经验内容 | 通过领域接口查询事实或提出受控操作 |
| Python Worker | 模型加载、图像推理、结构化输出与执行回执 | 消费派发消息，保存结果对象，回传原执行结果 |

五个领域服务采用Spring Boot，领域内部通过MyBatis-Plus及Spring事务访问MySQL；智能体运行采用AgentScope Java。视觉推理保留Python与PyTorch执行环境。划分的依据是业务规则和负载性质，而不是一个页面对应一个服务。

业务主站提供任务提交、复核和管理入口，智能工作台提供自然语言任务辅助。两类入口共用身份、领域接口与质量规则，分别保留现有Vue和React界面的职责。

### 1.2 以异步任务连接算法与业务

检测主链为：

```text
图像上传与来源登记
  → 模型及输入清单确认
  → 保存任务和待发事件
  → Kafka派发
  → Python Worker推理
  → 结果清单核验与任务更新
  → 人工复核和复核结果处理
  → 独立报告审批与交付
```

任务记录业务请求，调度记录一次实际检测安排，执行记录实际领取者。网络重投沿用原事件和调度身份；业务上重新检测则建立新调度，并保留与原任务的关系。

一次推理固定模型权重、程序版本、预处理、类别映射、阈值与原图清单。公共结果包含类别、置信度及原图坐标框；Catch-DEIM的实例掩码保留独立序列化与坐标语义，小样本方法的类别文本和正常支持记忆纳入模型部署清单。两种方法的Missing类别区域解释分别随模型版本保存。

## 2. 数据库划分、持久化与一致性

### 2.1 共享MySQL高可用集群，各服务独占领域数据

五个领域服务可共用MySQL高可用集群，但分别使用私有schema、最小权限账号及独立事务连接。其他服务经API或事件取得事实，不直接读写该领域的业务表。共用集群降低基础设施重复，数据所有权仍由业务责任决定。

| 所属服务 | 主要数据对象 | 修改责任 |
| --- | --- | --- |
| 资源 | 账号、员工、部门、设备、领用、告警 | 身份、组织和设备资料 |
| 模型 | 视觉模型、制品版本、部署清单和使用引用 | 模型准入及引用保留 |
| 检测 | 工作单元、输入、任务、调度、复核、后续处理、重复复查及历史汇总 | 检测与质量状态 |
| 报告 | 草稿、审批版本、事实保留及冻结交付 | 报告审核和交付 |
| 智能体 | 项目、会话、消息、运行、内容版本、连接器、LLM配置、额度及用量 | 专业执行、上下文与模型使用管理 |

微服务应用表按约40张作为初步设计预算，准确数量以逐表职责、约束和实际DDL清单审定，不能把估算写成已建库结果。该预算包括应用自建的回执、审计、队列及协调状态；现有单体29表重构不因论文方案调整而变更。Seata、Nacos和Langfuse的内部结构另列组件清单，并展示部署所需的完整总量。

### 2.2 通用机制复用代码，运行记录按领域私有持久化

命令回执、事务发件箱、审计及执行状态由使用它们的服务分别维护。回执保存原命令与处理结果，Outbox保存待发事件及投递状态，审计保存不可变业务变更，检查点和租约维护当前执行资格。定时计划与实际执行分别建模，不以一个通用流程表容纳不同业务生命周期。

幂等、投递及审计的程序库可复用，数据库账号只获得所属schema权限，不再采用跨领域公共表加存储过程的共享写入方案。本域业务、回执和事件在同一数据库事务中提交；AT分支的写入使用Seata支持且可被数据源代理完整追踪的SQL。

知识、Skills、SOP和经验仍可在智能体领域复用内容身份、不可变版本、片段及来源引用结构。各类型定义自己的发布规则和可见范围，这属于同一领域内相同内容生命周期的复用，与跨服务共享可写表不同。

### 2.3 用本地事务、Outbox与持久回执处理跨服务协作

业务状态与待发事件在同一本地事务中保存，后台将满足提交条件的事件发布到Kafka。参与Seata全局事务的事件先保持不可投递状态，按第2.6节的全局提交及分支确认门禁开放。消息允许重投，接收方通过原任务、调度和内容摘要定位原执行记录。

有副作用的命令以领域、账号、动作和原请求号定位；同号同内容返回原回执，同号异内容返回冲突。状态修改检查期望版本，执行领取检查所有者与代次。模型推理、远程调用及大文件读取在持锁事务之外执行。

跨服务协作采用持久引用与状态确认。例如报告先取得需要保留的检测事实，再形成审批快照；失败后依据原回执继续核对或补偿，不把远程超时直接解释为业务未执行。

原图、权重、预览和冻结报告保存在OSS，MySQL保存对象版本、内容摘要及业务关系。向量索引和缓存是派生数据，恢复时依据原始内容与版本重建。

### 2.4 统一采用Seata，按业务边界选择事务模式

**跨服务分布式事务统一采用Apache Seata：资源保留使用TCC，可补偿的自动业务流程使用Seata Saga，受支持的短时关系数据库写入使用AT。** 同一领域内能够在一个数据库事务完成的操作继续采用本地ACID事务，避免将额度账户等紧密不变量拆成多个远程分支。

多个服务共用MySQL集群，不代表RPC调用自动处于同一个本地事务。发起领域作为事务管理者（TM），Seata Server承担事务协调者（TC），各参与领域通过资源管理者（RM）登记分支和执行对应阶段。Seata全局事务号XID通过Dubbo Triple适配层传播；XID标识事务，原请求号标识幂等业务操作，二者均保留且不能互相替代。远程入口继续校验服务身份、用户范围与业务状态。

| 业务场景 | 事务边界与Seata模式 | 必须保持的业务条件 |
| --- | --- | --- |
| 企业与个人额度预留、结算 | 同一额度管理领域内的MySQL本地事务 | 双账户及流水共同提交，余额检查不跨服务拆开 |
| 创建检测并保留模型制品 | Seata TCC | Try登记准备态任务并预留模型引用，Confirm后达到派发条件，Cancel撤销本次未生效预留 |
| 报告快照与检测事实保留 | Seata TCC建立版本保留，人工审批作为独立业务阶段 | 审批针对固定快照，保留期间阻止冲突修改，人工等待不占用一个持续的数据库或全局事务 |
| 需要共同提交的短时跨服务SQL写入 | Seata AT | 写入经过受支持数据源代理，记录undo_log并遵守全局锁及版本约束 |
| 检测提交、结果整理和报告交付等自动步骤 | Seata Saga状态机引擎 | 定义正向服务、结果判断、补偿或前向恢复，耗时计算按业务任务身份分段衔接 |
| 任务状态与Kafka派发 | 本地事务写入Outbox，叠加Seata提交门禁 | 全局提交结论及必要分支确认满足后才开放消息投递 |
| 内容、OSS文件与Qdrant索引 | Seata Saga编排确认与可补偿步骤，索引异步更新 | 以业务版本和授权引用核验，补偿清理仅针对核实无有效引用的本次暂存资源 |
| 外部LLM调用与额度结算 | 本地预留及结算，自动处理阶段由Seata Saga衔接 | 外部已发生用量保留为事实，结果未知先核对原调用，不将补偿解释为供应商用量回滚 |

AT使用数据源代理、回滚日志和全局锁协调受支持的关系数据库操作；TCC由业务提供Try、Confirm及Cancel；Seata Saga以状态机定义正向服务与补偿服务，分支分别提交本地事务。[Seata AT](https://seata.apache.org/docs/user/mode/at/)、[Seata TCC](https://seata.apache.org/docs/v2.1/user/mode/tcc/)、[Seata Saga](https://seata.apache.org/docs/user/mode/saga/)

### 2.5 TCC资源事务与Seata Saga业务流程

检测创建采用TCC协调检测服务和模型服务。Try阶段保存准备态任务、固定模型与输入版本，并建立阻止制品回收的模型预留；Confirm将相应业务确认结果持久化；Cancel只撤销本事务尚未生效的准备记录和预留。模型引用已经确认且检测端确认成功后，任务才具备派发条件，不能依赖各分支Confirm恰好按某种顺序到达。

Confirm与Cancel使用Seata分支身份及稳定业务操作号实现幂等，结合TCC防悬挂记录处理空回滚和迟到Try。TC重试期间保留资源状态与回执；阶段结果未知时按XID和原命令核对，不仅凭客户端超时或租约到期删除保留。[Seata TCC Fence说明](https://seata.apache.org/blog/seata-tcc-fence/)

报告流程先通过短时TCC建立指定版本的检测事实保留和报告准备状态，完成确认后进入待人工审批阶段。人工审批不保持一个长时间打开的全局事务。审批提交后，以冻结快照及有效引用作为交付依据；通知丢失时恢复原审批状态，确需变更时建立新的业务修订记录。

自动化流程使用Seata Saga状态机引擎，而不是另写一套通用Saga执行器。流程定义包含节点、输入映射、成功判据、重试范围与补偿节点，并绑定固定定义版本。发起领域的业务记录保存操作身份、XID或状态机实例关联及对外业务状态；引擎定义、实例和步骤日志由Seata Saga自身持久化，分别承担业务事实与框架执行事实的记录责任。

状态机服务节点将回执未知映射到原命令核对或人工核对分支，不默认按失败重新调用外部模型或工具。有副作用的节点只在确认未执行，或原操作具有可靠幂等支持时自动重试；补偿操作同样核对原资源和执行身份。

模型推理和人工等待按任务、事件和持久业务状态分段推进，不让一个AT事务跨越整个检修周期。对已经产生结果、供应商用量或审批事实的步骤，恢复优先核对原回执并向前完成；仅为明确可撤销的资源定义补偿。Seata Saga不提供全局隔离，资源保留、状态和版本检查继续限制竞争操作。

### 2.6 Seata与Outbox共同控制提交和发布

Seata协调跨服务事务，Outbox解决业务数据库与Kafka事件之间的可靠衔接，两者职责不同。AT第一阶段的本地提交也可能发生在全局决定之前，因此消息发布不能仅由本地提交回调触发。

参与Seata事务的Outbox记录关联XID及原事件号，初始保持不可投递：

1. **AT分支**：取得确定的全局提交结论后开放发布；回滚或结果未知时不派发相应业务执行事件。
2. **TCC分支**：除全局提交决定外，继续核对派发依赖的Confirm结果。模型及任务等必要确认满足业务条件后，事件才转为可投递；不能仅因TC进入提交处理中就启动推理。
3. **Saga步骤**：以该步骤已持久化的业务结果及流程允许条件决定后续事件，不将消息发送当作数据库提交本身。

事件开放条件及变化使用持久版本检查。进程在全局提交后、事件开放前中断时，恢复任务依据Seata记录和业务回执继续开放原事件。重复发布、消费和完成回传沿用原事件与执行身份去重；Kafka消息不盲目继承一个长期开放的AT事务上下文。[Transactional Outbox模式](https://microservices.io/patterns/data/transactional-outbox)

### 2.7 Seata高可用、持久化与表数预算

Seata Server采用三个TC实例，分布在部署方案的三个故障域，与应用按资源配额混部。注册和配置通过Nacos管理，事务组映射到对应TC集群。协调器采用DB存储模式，将事务元数据保存到共用MySQL高可用集群的独立库和账号。三个TC实例共享该元数据存储，数据副本由MySQL复制机制维护。[Seata部署说明](https://seata.incubator.apache.org/docs/v2.4/ops/deploy-guide-beginner/)

事务持久化分为四类，使用所选Seata发行版的正式结构和迁移脚本：

| 数据类别 | 保存位置与用途 | 表数登记原则 |
| --- | --- | --- |
| 业务实体与操作回执 | 所属领域私有表，保存任务、模型、审批、额度及业务流程关联 | 应用实体及支撑表按实际DDL清点 |
| TC事务元数据 | 独立Seata库，保存全局事务、分支及锁等运行记录 | 计入基础设施表清单 |
| AT与TCC分支辅助记录 | 参与数据源的undo_log、TCC Fence等结构 | 按参与模式和数据源逐项登记，不能假设全部只建在协调器库 |
| Saga引擎记录 | 引擎配置的关系存储，保存定义、实例和步骤日志 | 使用正式引擎结构，业务表只保留必要关联 |

**应用自建表与组件内部表分别列清，同时展示完整物理表总量。** 微服务方案不承诺沿用单体29表总量；若仍要求全部活动表不超过30张，需重新评估功能和组件范围，而不是隐藏基础设施表。

Seata Server、客户端及Saga模块统一使用同一兼容发行版本，兼容性验证覆盖Spring Boot、Dubbo Triple及Nacos客户端。事务组、数据源身份、恢复权限及超时策略随发布配置管理。故障验证覆盖TC中断及接管、MySQL切换、分支回包丢失、Confirm/Cancel重放、补偿失败与Outbox提前发布，分别检查Seata事务状态和最终业务事实。

## 3. 单企业、多角色、多用户的权限体系

### 3.1 角色与具体业务责任分开建模

系统采用单企业组织目录，区分账号、员工与部门。核心业务角色为检测人员和主管；任务负责人、报告作者、审批人是具体对象上的责任关系，而不是为每一种操作新增角色。

检测人员访问本人及被分派任务，主管在授权业务范围内进行分派和复核结果处理。私人会话、工作区文件与个人运行历史按账号隔离，主管的管理职责不自动扩大为私人内容读取权限。

### 3.2 联合检查角色、资源、状态和版本

每次业务操作同时满足四项条件：

```text
允许操作 = 角色允许 ∧ 资源处于授权范围 ∧ 当前状态允许 ∧ 期望版本一致
```

Spring Cloud Gateway完成认证入口与路由控制，JWT令牌由JJWT处理，领域服务核验当前角色、对象范围及状态。页面按钮仅表达服务端返回的可用动作，最终写入仍由服务端判定。Dubbo Triple内部调用绑定服务身份、用户身份、目标操作和正文内容，避免仅凭来自内网就信任请求。角色、资源关系与审计事实保存在MySQL，权限机制不依赖新增独立身份管理服务器。

报告作者与审批人分离；审批针对冻结版本，内容变化需要新修订。智能体继承发起用户的访问范围，账号、角色和会话由服务端注入，不能由模型生成的参数决定。

### 3.3 将模型使用权与额度分开管理

“LLM模型管理”统一展示可用模型、额度、用量和申请。主管批准个人额度时，账户、流水与审计在同一事务提交；个人授额不增加企业总额度。

- 未设置个人额度账户的已有成员保留原有模型使用权，受企业额度约束。
- 设置个人账户后，调用同时受企业与个人额度约束。
- 可用额度为总量减去已结算用量和在途预留。
- 每次供应商尝试独立预留与结算；超时且结果未知时保留预留，按原调用核对实际用量。

模型重试、备用模型和经验蒸馏分别纳入调用预算，使自动化程度增加时仍有明确的资源约束。

## 4. 微服务治理、分布式高可用与性能保障

### 4.1 服务治理围绕寻址、过载和故障传播展开

Nacos提供服务注册、发现和配置管理。Spring Cloud Gateway承担业务API入口，Spring Cloud LoadBalancer根据发现的可用实例选择路由目标；内部类型化领域调用采用Dubbo Triple。Higress承担MCP及AI工具入口治理，普通业务REST请求走业务网关，领域授权保持统一。Nginx负责静态资源及反向代理，ALB负责节点健康路由，四者分别处在不同交互位置。[Spring Cloud Gateway官方说明](https://spring.io/projects/spring-cloud-gateway)、[Dubbo Triple官方说明](https://dubbo.apache.org/en/overview/reference/protocols/triple/)

限流与容错选用Resilience4j，在领域调用和外部模型调用处组合CircuitBreaker、Bulkhead、TimeLimiter、RateLimiter与Retry。它们管理当前应用实例的调用状态；集群总请求配额另通过Redis原子操作协调，不能将每实例相同的限额当作整个集群的总限额。[Resilience4j官方说明](https://resilience4j.readme.io/docs/circuitbreaker)

查询、视觉推理和外部模型调用划分独立资源域。入口请求速率、用户并发、在途推理任务及队列长度分别设置接纳条件。重试采用总时间预算与退避，有副作用操作先核对原回执。**Redis Sentinel只管理Redis故障转移；本方案的服务熔断、隔离与本地限流使用Resilience4j，两者职责不同。**

降级依据业务含义选择路径：查询可展示仍在授权范围内的带时效缓存；推理不可用时保留排队或失败状态；智能体不可用时保留业务页面与人工操作入口。质量结论必须来自真实检测及人工决定。

### 4.2 用三个故障域部署状态副本

目标拓扑采用三个独立故障域的ECS混部部署，应用多实例与状态副本分开管理，通过容器配额、独立数据目录和进程限制隔离资源。入口采用具备健康检查与故障转移能力的负载均衡，文件和独立备份使用节点之外的存储。

| 组件 | 本方案选择 | 一致性与故障处理 |
| --- | --- | --- |
| MySQL | 单主组复制，1个主节点、2个辅助节点，Router连接 | 关键读写路由主节点；失去多数派时停止相应写入 |
| Redis | 1主2副本，3个Sentinel，quorum为2 | 异步复制与自动故障转移，缓存可重建 |
| Nacos | 3个实例，配置元数据使用独立数据库账号 | 注册与配置服务跨节点运行，基础设施数据与业务表隔离 |
| Seata Server | 3个TC实例，Nacos注册配置，DB模式连接MySQL高可用集群 | 协调全局事务决策与恢复，客户端执行对应分支阶段 |
| Kafka | 分区副本因子3，`min.insync.replicas=2`，`acks=all`；3个KRaft Controller | ISR不足时拒绝相应写入，消费者按业务记录去重 |
| Qdrant | 集合副本因子3，写确认因子2 | 向量派生状态复制，读取仍核对内容版本与当前权限 |
| OSS | 保存原图、权重、结果、报告与版本化内容 | 以对象版本和业务引用核对，独立备份覆盖恢复需求 |

MySQL组复制提供单主选举及副本协同；新主接受关键业务前须满足积压应用的一致性条件，本方案显式检查`BEFORE_ON_PRIMARY_FAILOVER`或更高保证的配置。[MySQL官方一致性说明](https://dev.mysql.com/doc/refman/8.4/en/group-replication-configuring-consistency-guarantees.html)

Redis Sentinel的故障判定quorum与故障转移授权多数派是不同条件；Redis复制为异步机制，因此审批、额度和命令回执由MySQL保存。[Redis Sentinel官方说明](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/)

Kafka的`acks=all`对应当前ISR集合的确认，`min.insync.replicas`限定可接受写入的最小同步副本条件；消息持久化与外部数据库副作用去重分别处理。[Kafka设计说明](https://kafka.apache.org/40/design/design/)

Qdrant的副本配置与读写一致性参数分别作用于分布式数据访问；元数据共识不能代替业务权限和内容版本核验。[Qdrant一致性说明](https://qdrant.tech/documentation/scaling/consistency-guarantees/)

Nacos采用集群模式并使用MySQL保存配置元数据，配置库与领域业务库使用不同账号；其集群实例与客户端寻址共同参与注册配置服务的可用性。[Nacos集群部署说明](https://www.nacos.io/docs/latest/manual/admin/deployment/deployment-cluster/)

### 4.3 应用恢复检查执行资格，而不只是重启进程

任务领取、运行租约和代次持久化。旧节点失去租约后停止其运行，后续写入使用代次校验拒绝过期执行者。健康节点依据检查点建立新尝试，保留原中断记录；外部工具状态未知时查询原回执，避免恢复过程重复产生业务副作用。

CAP取舍落在具体状态上：关键业务写入优先保持授权与一致性，分区期间可以拒绝操作；缓存、检索和界面辅助在来源有效时保留有限服务。性能则通过异步计算、短事务、查询索引、缓存及有界并行改善，副本数量本身不等于吞吐提升。

磁盘预算分别计算业务数据、事务与消息日志、向量索引、镜像缓存和恢复暂存；完整副本在每个节点占用对应存储。节点规格以单节点失效后剩余节点的承载能力为约束，不仅按正常运行时的平均利用率配置。

## 5. AgentScope及其接入中间件

### 5.1 AgentScope承担运行编排，领域服务承担业务决定

选择AgentScope Java组织角色智能体、专业委派、工具事件和会话运行，与现有Java服务协作。框架提供的权限门控、事件与持久化扩展用于承接本系统机制，具体角色、资源范围、业务状态机和审批规则由领域服务定义。[AgentScope Java官方项目](https://github.com/agentscope-ai/agentscope-java)

| 依赖或协议 | 接入位置 | 本系统职责 |
| --- | --- | --- |
| MySQL、MySQL Router | 会话、运行及领域持久化层 | Router连接可用主节点，MySQL保存权威业务事实、运行资格、审批与额度流水 |
| Redis | 缓存与辅助协调适配层 | 热点查询和可重建状态，减少重复读取 |
| Kafka | 检测领域事件与执行通知适配层 | 派发推理、回传结果、通知对应任务和会话 |
| OSS | 文件与内容适配层 | 原图、权重、报告、附件及大体量上下文卸载 |
| Qdrant | 语义检索适配层 | RAG、长期记忆与经验条目的向量检索 |
| Mem0 | 长期记忆适配服务 | 记忆提取、合并及召回策略，保留用户与来源范围 |
| AgentScope模型扩展、受管模型接口 | 模型管理与调用治理层 | 对话、记忆提取和嵌入分别登记、路由与计量 |
| MCP、Higress | 工具协议与入口治理层 | 连接允许的外部工具，传递受限身份和操作 |
| Docker运行器 | 工具执行层 | 子进程、文件范围、网络和资源隔离 |
| AG-UI、A2UI | 智能工作台交互层 | 流式执行事件及受限结构化界面 |
| Nacos、Dubbo Triple | 配置及领域调用层 | 发现领域服务，经内部契约访问当前授权业务事实 |
| OpenTelemetry、Prometheus、Langfuse | 观测层 | 关联业务与智能体执行，分别监测系统指标及模型、检索和工具调用 |

依赖关系以适配接口进入系统，智能体不能绕过领域服务直接修改任意数据库表。Kafka承担业务异步事件，并不要求每一次模型推理或工具读取都经过消息队列。

具体调用关系为：

```text
业务页面 → ALB/Nginx → Spring Cloud Gateway → 领域服务
智能体 → 授权领域工具 → Dubbo Triple → 领域服务 → MySQL Router → MySQL
智能体 → 模型管理与额度层 → AgentScope模型适配 → 登记的模型服务
智能体 → MCP适配 → Higress → 受限Docker工具运行器
智能体 → 记忆适配服务 → Mem0 → Qdrant
检测服务 → Outbox/Kafka → Python Worker → OSS/结果事件 → 检测服务
```

长期记忆的LLM与嵌入模型分别配置：LLM负责提取和整理记忆，BGE-M3负责向量化，Qdrant负责向量存取；三者不能用一个“记忆模型”配置笼统代替。对话、嵌入及记忆提取调用统一登记身份、来源和预算。

### 5.2 RAG、长期记忆和经验共用向量设施，分别保存语义与权限

向量存储统一选择Qdrant，知识片段、用户记忆和专业经验使用分离的集合或命名空间，分别保存内容版本、账号、可见范围与来源标识。Mem0支持Qdrant作为向量存储；本方案在其外层补充领域权限与来源核验。[Mem0的Qdrant配置](https://docs.mem0.ai/components/vectordbs/dbs/qdrant)

嵌入采用BGE-M3的1024维稠密表示，模型标识、处理方式和内容版本共同确定索引版本。同为1024维的不同模型输出不能据维度相同而直接混用；更换嵌入模型时以原始内容重建新索引。[BGE-M3官方模型卡](https://huggingface.co/BAAI/bge-m3)

RAG回答“有哪些可靠资料”，长期记忆保存与用户或任务相关的稳定上下文，经验记忆回答“相似任务如何更有效地处理”。检索先过滤可见范围，召回后重新检查当前权限、来源和版本，已删除或失效内容不得因旧索引仍存在而继续展示。

### 5.3 Mem0历史状态与向量副本分别处理

Mem0开源Python实现的历史管理使用SQLite；将向量库改为Qdrant并不会同时完成历史状态的多节点共享。[Mem0历史存储源码](https://github.com/mem0ai/mem0/blob/main/mem0/memory/storage.py)

本方案将记忆操作封装为独立适配服务，统一处理身份、原请求号和版本。面向多节点接管，历史存储采用需要定制的共享持久化适配，将历史变更及幂等记录落入受控关系存储；该扩展与向量库配置分别实现和验证。原始SQLite历史作为迁移来源保全，活动SQLite文件不作为跨节点共享写入载体。

### 5.4 可观测性采用OpenTelemetry、Prometheus与Langfuse

系统运行异常与智能体决策问题需要不同的观察视角。接口变慢可能源于资源竞争、任务积压，也可能源于模型响应、检索或工具调用。为使诊断同时覆盖系统与专业任务，采用OpenTelemetry统一埋点和上下文传播，Prometheus保存系统指标，Langfuse呈现智能体执行及评价结果。

埋点记录关键操作的开始、结束、耗时和错误；采集将这些记录及指标发送给对应后端；上下文传播让同一请求经过网关、领域服务和工具时保留可关联的Trace ID，各环节分别形成Span。OpenTelemetry提供生成、采集与导出规范，数据存储和分析由后端承担。[OpenTelemetry官方定位](https://opentelemetry.io/docs/what-is-opentelemetry/)

| 位置与职责 | 具体组件 | 本系统中的记录与用途 |
| --- | --- | --- |
| 统一埋点与上下文传播 | OpenTelemetry SDK及应用集成 | 关联网关、领域调用、智能体运行、检索和工具步骤，记录耗时及错误 |
| 应用指标埋点 | 现有Micrometer及必要的指标导出器 | 在应用内产生接口、JVM及任务指标，保留既有埋点，不作为独立监控服务部署 |
| 系统指标与规则计算 | Prometheus | 抓取接口时延、错误率、任务积压、Worker及中间件状态；主机指标按需由node_exporter提供 |
| 智能体与模型观测 | Langfuse | 查看专业委派、检索、工具与模型调用，记录模型及提示词版本、token用量、时延、反馈和评分 |
| 运行日志 | 应用结构化输出、日志轮转、OSS归档 | 记录请求、任务、调度、运行及Trace ID，按来源检索和回溯 |
| 告警通知 | Alertmanager | 接收Prometheus规则产生的告警，完成分组、去重及通知路由 |

默认数据路径为：

```text
Java/Python应用内埋点
  ├─ 指标端点 → Prometheus抓取与规则计算 → Alertmanager → 通知接收端
  ├─ 智能体及相关业务Span → OTLP/HTTP → Langfuse
  └─ 结构化日志 → 轮转与归档 → OSS
```

业务调用与智能体Span通过Trace ID及运行标识关联。异步检测、重试和人工审批通过任务号、调度号、运行号关联各次调用，不强制将整个检修周期组织成一条长期存活的Trace。Prometheus采用服务、接口、状态等有界维度，逐请求Trace ID及任务号保存在Span和日志中，避免将其作为高基数指标标签。

Langfuse使用OTLP/HTTP接收调用链，不承担OpenTelemetry日志或指标存储，也不提供Span Links的展示；异步来源关系保存为明确的业务字段与引用。[Langfuse支持的OpenTelemetry信号](https://langfuse.com/faq/all/opentelemetry-logs-metrics-span-links)

本方案默认由应用直接向对应后端导出数据，OpenTelemetry Collector仅在需要统一转换、脱敏或多后端分流时部署。Jaeger与VictoriaLogs移出默认选型，日志通过轮转及OSS归档保留，按业务编号定位原始记录。Prometheus计算告警规则，Alertmanager负责通知发送。[Prometheus告警机制](https://prometheus.io/docs/alerting/latest/overview/)

Langfuse的反馈与评分关联模型、工具目录、SOP及经验版本，为并行、流程复用和自进化的对照评价保存观测。评价默认使用人工反馈和确定性检查，模型判分调用单独配置预算。上报内容按用途筛选和脱敏，保留必要业务编号，不默认上传凭据、原图及完整敏感业务正文。业务审计、审批及额度事实继续由MySQL保存。

### 5.5 Langfuse自建依赖与观测资源预算

OpenTelemetry、Prometheus和Langfuse是三个职责模块，不是三个容器。Langfuse自建包含Web及Worker，并依赖PostgreSQL、ClickHouse、Redis或Valkey，以及S3兼容对象存储。[Langfuse架构说明](https://langfuse.com/handbook/product-engineering/architecture)

| Langfuse依赖 | 保存或处理的内容 | 与业务基础设施的关系 |
| --- | --- | --- |
| Web与Worker | 观测接收、界面查询与后台处理 | 按入口与处理负载配置资源，分别计入容器预算 |
| PostgreSQL | 用户、项目、提示词和评价配置等事务数据 | 独立观测库，业务MySQL不能直接替代 |
| ClickHouse | 调用观测、评分及其分析查询 | 独立分析存储，按观测量、保留期和副本数计算容量 |
| Redis/Valkey | 观测任务队列及缓存 | 队列需匹配持久化及禁止淘汰等要求；只有隔离、配额和故障策略满足时才复用现有Redis，否则使用独立实例 |
| S3兼容对象存储 | 原始摄取事件、附件与导出内容 | 使用专用存储范围与凭据；复用OSS入口时验证所需上传、读取及预签名行为 |

对象存储按Langfuse实际使用的S3接口配置，接入验收覆盖服务端及浏览器访问、上传下载、预签名、生命周期与权限。[Langfuse对象存储配置](https://langfuse.com/self-hosting/deployment/infrastructure/blobstorage)

部署预算单列Prometheus时序数据、Langfuse关系数据、分析数据、队列及对象内容，并明确采样、保留周期、清理和恢复策略。Langfuse应用副本与存储高可用分别配置；PostgreSQL、ClickHouse和队列的副本及故障切换方案纳入观测资源设计，不能由业务MySQL的三副本推断它们已经高可用。

观测系统故障时，业务操作与审计仍按各自持久协议执行，上报采用有界缓冲和明确丢弃统计，避免遥测阻塞推理或审批。Langfuse内部表与Seata等框架表一样单列统计，并纳入完整部署清单。

## 6. 多智能体建模与专业任务并行

### 6.1 角色入口与专业能力分离

员工和主管分别使用对应主智能体入口。主智能体理解目标、选择能力并归并结果；专业智能体负责任务查询、质量核对、设备资料、工作量分析或报告整理等限定任务。专业角色由工具范围、输入输出及上下文定义，不要求每个角色配置不同的大模型或独立服务器。

委派保留原用户、会话、父子运行、业务对象与工具调用关联。工具返回结构化事实及来源，主智能体据此组织回答；实时业务状态通过领域工具读取，不能用历史记忆替代。

### 6.2 按数据依赖与操作冲突组织并行

复合请求拆分为具有明确输入、输出和前置条件的子任务。无依赖的读取并行执行；依赖已取得事实的步骤按顺序推进；对同一对象的竞争写入通过状态和版本串行化。

例如“汇总今日任务、核对异常设备并整理报告草稿”中，任务统计与设备查询可以并行，草稿整理依赖两者结果；报告审批仍由具备职责的另一人员完成。

不同会话分别持有运行状态，同一会话保持单一有效主运行，子任务通过父子关系汇总进度。并发数同时受工具资源、模型额度和系统负载约束，避免扇出调用放大资源竞争。

### 6.3 人机协同控制具有副作用的操作

检测创建、质检分派及重试等动作先形成结构化提议，再经用户确认。确认绑定用户、对象、动作、参数及版本，提交时重新授权；内容改变需要重新确认。模型负责解释和准备，领域服务负责实际业务决定。

AG-UI传输运行、消息和工具事件，A2UI使用固定组件目录表达任务、统计和确认入口。界面事件映射到注册动作，不执行模型生成的任意脚本或任意接口。

## 7. SOP复用、工作流与上下文管理

### 7.1 将标准作业程序转化为可追踪执行

SOP即标准作业程序，描述适用对象、输入条件、必要步骤、责任角色、确认点、结果要求及异常处理。SOP是业务规范，工作流实例是一次实际执行，运行轨迹记录实际发生的操作，三者分别持久化并通过版本关联。

SOP定义保存在版本化内容中，执行实例绑定所使用的SOP版本及当前业务对象。运行前核对权限、工具能力和前置条件，执行中保存步骤结果及原请求回执；中断后依据已完成事实恢复，具有外部副作用的步骤先核对原执行。

Skills描述专业能力及工具使用规则，SOP组织跨步骤业务规范，二者结合减少重复规划。质量审批等强制步骤由状态机检查完成条件，不能只依赖提示词要求模型记住。

### 7.2 按有效信息组织上下文

上下文由当前任务事实、相关资料、必要历史摘要、适用SOP和经验条目组成。大文件、完整工具输出及历史轨迹保存在OSS或受控持久层，模型上下文保留摘要和授权引用。

摘要保存来源及版本，关键业务值实时查询。长任务使用检查点记录进度，恢复时重新检查当前权限与对象状态，避免旧上下文导致过期操作。

## 8. 反馈反思、经验记忆与智能体自进化

### 8.1 采用固定模型参数的经验驱动适应

本方案中的自进化作用于专业路由、工具选择、步骤组织和经验召回，不改变大语言模型权重。Reflexion提供通过语言反馈与情景记忆影响后续决策的研究基础；ReMe的记忆蒸馏用于参考经验整理方式。[Reflexion论文](https://arxiv.org/abs/2303.11366)、[ReMe经验蒸馏说明](https://github.com/agentscope-ai/ReMe/blob/main/docs/en/auto_dream.md)

更新闭环为：

```text
执行轨迹与业务回执
  → 人工纠正、失败归因及结果反馈
  → 提炼适用条件与有效步骤
  → 来源、权限和冲突检查
  → 固定任务集回归评价
  → 发布经验版本
  → 相似任务检索与受控应用
```

### 8.2 经验保存适用条件，而不是复制历史答案

经验条目保存任务类型、前置条件、专业委派、工具顺序、结果依据、失效条件及来源运行。以单任务状态查询为例，错误地调用企业工作量统计后，可从人工纠正与真实任务回执中提炼“单任务问题使用任务详情工具”的路由经验。

再次使用时核对当前工具、用户权限与任务范围；旧经验中的状态不作为当前事实。相似经验合并，矛盾条目核查修订，过时经验停用并保留版本。个人经验与企业共享经验分别授权。

### 8.3 用版本评估决定发布与回退

经验更新固定语言模型、工具目录及评价任务，分别比较无经验记忆、普通历史记忆和反馈优化经验。指标包括任务完成率、路由错误率、无效工具调用、事实一致性、时延与token成本。

评价任务与经验构建样本分离；新版本同时检查目标收益和其他任务回归。发布后保留旧版本及来源，错误经验按版本停用或回退。审批规则、角色权限和复核通过条件由领域服务维护，经验更新不修改这些业务约束。

## 9. 部署、数据恢复、交付与验证

### 9.1 本地编辑构建，ECS承担运行与测试

本地Jenkins检出已提交推送的固定版本，完成编译打包，通过SSH/SCP调度ECS运行测试和部署。源码、制品、配置版本与原始报告关联同一提交及构建身份。流水线检查目标就绪和执行身份，ECS保持开启，生命周期由用户管理，不由流水线或助手自动启停；云盘与其他保留资源按其独立生命周期管理。

单体与微服务使用各自隔离的运行配置及数据入口，数据迁移通过明确的复制、核验和切换协议完成。

Docker Compose描述每个ECS上的容器及网络，MySQL、Redis、Kafka和Qdrant分别按自己的集群协议复制与接管。Compose不承担跨主机调度，不因使用Compose就具备节点级自动故障恢复。

### 9.2 数据迁移以恢复能力和业务关系为验收对象

数据库重构保留原始编号、空值、时间精度、文本及密文字节、唯一约束和来源关系；原库备份和目标库备份分别恢复验证。文件按业务引用核对实物，历史Windows路径通过来源映射确认，目录名称不同不直接认定文件缺失。

知识、记忆与经验保留原内容、历史及权限，再建立目标索引；旧Kafka文件作为历史档案保存，不直接当作当前集群活动日志装入。切换时冻结写入并确定唯一写入者；新系统开始运行后的失败通过目标恢复或前向修复处理，避免重新开放旧库产生双写。

## 10. 本方案的审阅重点

建议优先确认以下五项架构决定，它们直接影响实现方式及论文表述：

1. **服务与数据库的关系**：采用五领域服务及独立推理平面，数据库共用高可用集群，各服务独占领域表及运行记录；通用机制复用代码，不跨域共享写入。
2. **AgentScope的职责边界**：框架组织协作与运行，中间件提供持久化和治理，领域服务保存业务事实及最终授权；Mem0历史层与向量层的多节点适配分别落实。
3. **第三个工作的研究主线**：算法服务化解决企业可用性，分布式治理解决运行保障，权限与版本记录解决安全追溯，专业协同、SOP及经验更新解决操作效率和经验复用。实验分别回答这些问题。
4. **Seata事务模式与表数口径**：跨服务事务采用Seata，按TCC、Saga和短时AT区分场景；应用表约40张为设计预算，单体29表不随之变更，协调器和分支辅助结构纳入完整清单。
5. **观测主干与真实依赖**：采用OpenTelemetry、Prometheus、Langfuse，保留日志归档及Alertmanager通知；Langfuse的PostgreSQL、ClickHouse、队列和对象存储单独计入资源、表数与高可用预算。

编写依据：本目录《写作规则.md》、论文第五章`tex/chap5.tex`、现有数据模型，以及项目`feature/microservices`分支的POM和容器配置。`compose.observability.yml`用于核对既有埋点及参考配置，本技术方案的观测选型以第5.4—5.5节为准。外部组件机制参考文中的官方资料；服务归属、领域内持久化及任务协作方式是本方案的设计选择。
