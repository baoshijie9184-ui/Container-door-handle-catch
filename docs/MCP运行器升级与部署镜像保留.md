# MCP 运行器升级与部署镜像保留

2026-10-22 UTC+8，`java-cloud`。当前为源码实现状态：未执行脚本、编译、测试、构建、迁移、Jenkins 或云端操作。共享镜像回收开关保持默认关闭。

## 发布顺序

`script/docker/mcp-runtime.py` 接入现有 Jenkins 发布锁，与应用、记忆桥接一起编排固定 Fetch 运行器。只使用宿主已存在、通过固定版本和包摘要标签核对的不可变镜像，不自动拉取，不提供任意镜像或命令入口。

1. 读取真实容器镜像、代次、运行状态、命名卷和已审核版本列表，保存原镜像快照。目标必须保留原 journal 卷、固定网络、隔离配置及同一签名凭证；凭证轮换需独立协调。
2. 写入私有 PREPARING 记录，在 V60 可用时先锁定镜像并保存过渡保留引用，然后停止原 nginx、backend、Higress 和 runner。未能核实代次不继续。
3. 确认卷没有其他运行中的写入者，用已审核镜像中的固定 Python 读取停止后的 SQLite 有界副本，包括 WAL。探查容器无网络、只读挂载原卷、有内存/进程/CPU 限制；不启动 SDK、Fetch 服务或工具。
4. 根据数据库、持久协议 pin 和 journal 取最高要求。目标 runner 不兼容时保留现有兼容 runner，并同步后台目标及审核列表。没有兼容版本则停止发布。
5. 保存 PREPARED，再在 Compose 变更前记录 APPLYING。仅替换 runner 服务，保留卷，不构建、不拉取；验证镜像、健康、卷绑定及原 pool 后记录 VERIFIED。随后沿用记忆、后端和网页激活流程。
6. 应用健康后，先写入一个 fsync 的权威发布记录，再生成旧版目录/镜像指针，最后提交镜像保留基线并记录 FINALIZED。启动下次发布时从权威记录补齐兼容指针，避免中断后混用新旧文件。

VERIFIED 只证明该步骤观察到的 runner 身份、卷及健康，不代表整体业务验收通过。Jenkins 公开产物仅保留状态、请求尝试、不可变镜像和计数，不包含完整 Compose、环境变量、pool 或服务器路径。

## 镜像保留与协议

V60 在 MySQL 增加部署引用、控制行及事件，并给镜像命令增加 `retention_protocol`。新回收协议要求后端声明 4，runner 声明 `io.doorhandle.mcp-image-lifecycle=2`，签名带 `image_policy=4`；runner 准备回收时持久记住此下限。原生协议 2、旧共享回收协议 3 的历史读取仍保留。

发布中旧/选定镜像登记为 TRANSITION 保留。发布成功后，当前与上一版本分别占用固定保留槽，两槽及过渡引用参与共享回收的同一镜像锁检查。只有发布回执和基线提交后才释放旧过渡引用。发布失败留下的引用保守保留，到后续成功发布才解除；不把断线等同于镜像不再被引用。

控制行最初为 COLLECTING。未成功建立保留基线前，主管卡片显示基线未核对并阻止回收。重复发布回执必须仍对应受保护镜像及 ACTIVE 基线，不能仅凭事件存在判定完成。候选环境仍禁止删除宿主共享镜像。

## 中断与恢复

每次尝试保存独立编号及递增版本，私有历史最多 10000 份，达到上限要求显式归档。文件包含恢复所需的实际 runner 环境，按 0600 保存，必须按凭据资料保护与备份；不能纳入公共 Jenkins 产物。

停止前失败，仅核实原容器代次和运行状态。停止后失败，先停止本次已知 runner、重读 journal，确认旧 runner 与旧后端都能读实际协议及原 pool，再恢复原 runner 和同代次的原服务。不能证明时保持 NEEDS_REVIEW，保留卷和证据，不删除目录、不重放执行。自动恢复应用使用独立尝试，关闭失败发布但不把它写成成功版本。

已 VERIFIED 却未发布的尝试，不能被下一次正常发布直接覆盖；只有明确恢复原应用的路径可以继续。发布记录已提交而保留基线未完成时，保守引用继续生效，允许核对同一尝试完成 finalization，不自动再执行业务写入。

隔离演练启动复制卷前还会拒绝复制库或 journal 中的未结束 MCP 执行，防止候选环境按旧 pool 操作生产资源。该限制不是已经完成的演练证据。
