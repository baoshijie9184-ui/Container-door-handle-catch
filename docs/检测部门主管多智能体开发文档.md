# 检测部门主管多智能体开发方案

## 1. 目标与边界

本方案面向检测部门主管（多人）提供管理、复核和质量决策辅助。主管智能体可以查看部门汇总数据、审批员工提交的复核结果、生成质量分析报告和安排复检，但最终质量签署仍由具备对应业务权限的主管人工确认。智能体不自动发布结论、不修改模型生产配置、不绕过 RBAC。

主管 Agent 与普通员工 Agent 分开注册：`supervisor-assistant`。两者共享只读知识检索能力，但使用不同的 Tool Policy、Skills 和数据范围。

## 2. 专用智能体

| Agent ID | 职责 | 关键输出 |
| --- | --- | --- |
| `supervisor-assistant` | 入口编排、意图识别、审批流程编排 | 管理答复、待办、风险提示 |
| `quality-overview` | 部门/班组/时间段质量指标分析 | 良率、缺陷趋势、异常 TopN |
| `review-approval` | 复核申请审阅、证据汇总、审批建议 | 通过/驳回建议及理由 |
| `reinspection-planner` | 根据异常和设备状态制定复检计划 | 批次、人员、设备和优先级 |
| `report-publisher` | 生成正式报告候选稿、版本差异和发布检查清单 | 待签署报告 |
| `risk-compliance` | 越权、敏感数据、质量红线和提示词注入检查 | 阻断/升级/脱敏决定 |

编排规则：查询类请求可自动执行；审批、发布、批量导出、调整阈值等写操作必须先输出确认卡片，并要求当前主管重新确认。涉及跨部门或生产模型的操作升级到人工流程。

## 3. 主管工具白名单

允许：`detection.task.department-summary`、`detection.result.trend`、`detection.review.pending`、`detection.review.detail`、`detection.review.approve`、`detection.review.reject`、`detection.reinspection.create`、`detection.device.health-summary`、`model.catalog.compare`、`report.quality-draft.generate`、`report.quality-draft.save`、`report.publish.prepare`、`knowledge.search`。

禁止或需更高权限：用户/角色管理、删除任务、删除原始图片、模型上传/发布/回滚、修改检测阈值、跨租户导出、最终质量签署（若系统存在独立签署权限）。

所有工具参数使用请求 DTO，并由 `SupervisorToolPolicy` 校验 `tenantId、departmentId、roleCodes、resourceIds、approvalId`。审批工具必须带 `expectedVersion`，防止并发审批覆盖。

## 4. Skills

```text
doorhandle-module-ai/src/main/resources/skills/supervisor/
├─ base/SKILL.md
├─ quality-analysis/SKILL.md
├─ review-approval/SKILL.md
├─ reinspection-planning/SKILL.md
├─ report-publishing/SKILL.md
└─ compliance-escalation/SKILL.md
```

每个 Skill 记录版本、适用角色、数据范围、允许工具、审批条件、红线规则和引用来源。质量分析 Skill 必须声明统计口径（样本数、缺陷率分母、时间窗口）；审批 Skill 必须要求图片/结果/员工说明等证据齐全；发布 Skill 必须检查报告版本、数据截止时间和未关闭风险。

## 5. 会话和审批隔离

会话键：`agent:session:{tenantId}:{userId}:{sessionId}`。主管可查看部门聚合数据，但不能通过会话读取员工的私聊内容或其他部门草稿。审批记录单独保存：`agent:approval:{tenantId}:{departmentId}:{approvalId}`，并关联申请人、审批人、版本号和审计 traceId。

审批流程使用状态机：`PENDING → APPROVED | REJECTED | EXPIRED`。审批结果必须由当前登录主管提交，模型只能生成建议。批量操作采用预览—确认—执行三步，执行阶段重新校验权限和数据版本。

## 6. 典型流程

1. 主管通过 AG-UI 调用 `supervisor-assistant`。
2. 入口从 Spring Security 上下文构造 `RuntimeContext`，确认主管角色和部门。
3. `risk-compliance` 检查输入，加载对应 Skill。
4. 编排器调用质量分析或复核 Agent 获取事实和引用。
5. 写操作先返回影响范围、证据和确认卡片。
6. 主管确认后，工具层使用幂等键和乐观锁执行。
7. 返回结果、审计编号和下一步待办。

## 7. 验收标准

- 普通员工 Token 无法发现或调用主管 Agent 与主管工具。
- 审批/发布不会因模型输出自动落库，必须存在人工确认事件。
- 跨部门查询只返回授权聚合结果，不能下钻到未授权明细。
- 并发审批返回版本冲突，不覆盖其他主管决定。
- 所有指标可追溯到任务 ID、统计口径和数据截止时间。
