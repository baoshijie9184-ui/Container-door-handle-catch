# 固定 Fetch 共享镜像回收

2026-10-22 UTC+8，`java-cloud`。状态：新增源码、V59 迁移副本、配置与页面，未编译、测试、构建、运行脚本、迁移或部署。下面描述实现约束，不是生产验收结果。

## 范围与模块

只处理部署登记的固定 Fetch 不可变镜像 ID，最多八个已审核版本。当前运行镜像拒绝回收；保留原 AgentScope Java SDK、权限和用户安装生命周期，不开放任意 Docker 命令、镜像、路径或 MCP 注册。

App 的 `FetchSharedImageController` 通过 contracts `AgentMcpImagesApi` 调用 AI 的 `FetchSharedImageService`；App 只负责 HTTP 与受信账号身份，AI 维护自己的引用、封存、命令和审计表。主管角色在入口与每个关键执行阶段重新核对，员工不能读取跨账号引用统计。响应不含其他用户 ID、安装正文、绝对路径、pool 或签名凭证。

主管在原 MCP 管理页查看共享镜像卡片，独立 React 沿用现有管理页面链接。卡片展示运行器观察、镜像逻辑大小、当前登记/回退保留/未知快照/未退出执行/全系统未结束安装计数，以及许可证归档字节。时间使用 UTC+8，提供键盘焦点、手机布局和减少动画样式；实际效果未做浏览器验收。

## 引用保护与封存

V59 增加 `agent_fetch_image` 和 `agent_fetch_image_command`，为执行账本增加 `image_id`。每个镜像有独立版本、原回收请求、原操作账号、runner pool 和归档摘要。保留这些字段及历史，应用回滚不删除。

开始回收前锁定对应镜像，核对所有账号的当前安装登记、回退保留和安装退出证据；未清理执行、未知旧执行镜像及未结束安装也会阻止回收。未知快照不能按零引用处理。新安装与执行在保存业务状态的同一事务中核对镜像封存行。镜像进入 RETIRING 后，禁止建立新的受控引用。

V59 表已存在时，即使关闭新回收页面，当前代码仍执行引用封存读取；不能通过关闭页面开关绕过已有封存。没有 V59 且功能关闭时保留原路径；开启新能力但迁移不完整时拒绝启动或操作。

SQLite 执行 journal 新增镜像封存与事件记录，执行预留和封存核对使用同一事务。这样旧签名请求、正在连接的 SDK 和多运行器也不能在封存之后登记新的执行。MySQL 与 SQLite 各自有持久证据，不用内存集合替代跨进程协调。

## 一次回收的顺序

1. 用户确认镜像与版本，提交 UUID 请求编号。相同编号只返回既有结果，修改内容使用同一编号会被拒绝。
2. MySQL 同事务提交 RETIRING、原账号/请求/pool、命令及必要审计，之后才请求 runner 准备。runner 核对已审核镜像、实际版本/包摘要标签及当前镜像排除，持久封存后再次检查执行是否全部清理。
3. runner 返回 PREPARED 后，AI 再次鉴权、锁定同一镜像并重查全系统引用，将删除批准与审计提交，再发送一次删除请求。未知提交结果不自行重做。
4. runner 在 SQLite 中独占领取这次回收，先记录 ARCHIVING，再创建固定、从不启动的法律资料快照容器；不运行该镜像的程序。只读取三个固定位置：manifest、依赖锁和 licenses。
5. Docker cp 输出按读取过程限制大小，tar 不解压到宿主；拒绝链接、特殊项、越界路径、重复文件和未登记条目。逐份核对 manifest 中的许可证摘要，保留完整文字、依赖锁及 manifest，编码为私有归档文件，fsync 文件与目录，再持久保存归档摘要。
6. 仅按本次创建并核对的不可变容器 ID 删除停止的快照容器；再次确认不存在容器引用后，提交 `docker image rm --no-prune`，不带 force，不清理父镜像。创建与执行均指定禁止自动拉取。
7. 通过实际 daemon 查询确认镜像不存在，并重新读取已保存归档核对摘要后，才记录 REMOVED。SQL 最终状态、必要审计与命令回执同事务提交；并发旧观察不能覆盖已核实摘要或把完成状态降回未知。

实现参考 Docker 官方 [镜像删除说明](https://docs.docker.com/reference/cli/docker/image/rm/) 与 [容器复制说明](https://docs.docker.com/reference/cli/docker/container/cp/)。未引用检查是应用策略，Docker 的拒绝删除仍是额外保护；不使用 prune 或强制删除绕过引用与多标签冲突。

## 未知结果与隔离边界

超时、断网、进程退出、审计失败、归档不完整、多标签冲突或 Docker 状态无法核实时，继续保持封存和 NEEDS_REVIEW。查询原回执只观察资源与已经保存的归档，不再创建快照容器、复制文件或重发镜像删除。能独立证明镜像已不存在且法律归档完整时，才补齐最终状态；不能证明则继续待核对。

若中断留下法律快照容器、部分归档或丢失 journal，没有自动强制处理入口，需保留现场并走后续受控运维核对。清空 journal、删除 SQL 行或补写“已退出”不能作为恢复方法。普通主管的只读核对可以解析另一位主管原先提交的全局技术操作，但签名身份仍绑定 SQL 保存的原账号、原请求和 pool。

候选环境与生产共用宿主 daemon，候选数据库不包含生产的实时引用。为防误删，runner 在准备和删除前核对自身容器代次、固定生产 Compose 项目/服务、实际镜像和既有执行卷；候选环境仅允许观察，API 也会拒绝其删除请求。真实删除正向验收必须使用有完整引用账本的生产受控数据，或另行准备独立 Docker daemon，不能拿候选库的零引用替代生产证明。

封存是持久的版本退役，不因外部重新导入同一 ID 而自动恢复。当前或回退保留版本不能被回收；用户先主动解除回退保留并清理后，不再保证能够直接回退到该版本。重新批准已退役 ID 不在本次自动流程中，部署守卫也禁止把待核对或已退役镜像设为当前目标。

## 存储与发布

归档位于现有 runner 执行持久卷内的私有法律资料目录，不在可清理的用户安装目录，也不再依赖即将删除的镜像。每份归档至多 16 MiB，runner 最多登记 128 个退役镜像；达到容量后拒绝新增，不自动删除法律资料。归档字节单独显示，整个卷仍需现有磁盘监测和备份。该限制不是操作系统硬配额。

Docker 镜像大小包含共享层，不能等同于本次实际释放字节，更不能推算计费。接口的 `reclaimedBytes` 保持未知，控制台只报告观察到的镜像存在状态和归档摘要。

新开关 `AGENT_MCP_SHARED_IMAGE_CLEANUP_ENABLED=false` 同时传给后端及 runner。仅 GATEWAY、持久安装队列、执行回执、生命周期和安装核对共同启用后允许使用。`AGENT_MCP_WRITES_ENABLED=false` 同时暂停新的共享回收，保留历史及原回收只读核对。

当前源码后端协议声明为 4，runner 声明 `io.doorhandle.mcp-image-lifecycle=2`。V60 增加部署当前/上一版本及过渡保留引用，未建立保留基线前阻止回收。发布守卫读取封存与命令历史并持久提升格式下限；已有退役状态不能回滚到忽略封存的旧应用或运行器。Jenkins 与隔离演练已接入运行器升级编排源码，见 [升级与镜像保留](MCP运行器升级与部署镜像保留.md)。首次启用仍需独立兼容恢复基线；本轮没有创建或更新服务器镜像。

原本地 MCP 迁移辅助脚本新增 `--shared-images` 和 `--native-install`，当前生命周期选择也包括 V58。它仍仅面向明确配置的本机演示库，只有显式 apply 才写入。本轮未运行；其选定列检查不能替代服务器完整迁移签名和回滚演练。

现有备份源码会停止含 runner 在内的业务写入者并保存实际命名卷；法律归档需随原 journal 一起恢复。停止后的未知 Docker 操作不自动重放。最终备份、恢复和运维定时单元的联合验收仍未执行。
