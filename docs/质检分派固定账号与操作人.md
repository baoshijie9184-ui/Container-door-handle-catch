# 质检分派固定账号与操作人

日期：2026-10-22，UTC+8。分支：`java-cloud`。

本轮为新增实现代码，未编译、测试、构建、执行迁移、启动服务或部署。完整五类单体功能仍在开发，本文件不作为候选或生产验收证据。

## 责任人不是一个可重新解释的名称

原确认提议只保存责任人名称。现在预览通过 System 账号门面取得精确唯一的员工账号 ID 和账号快照摘要，把它们固定到 `DetectionAssignmentApi.Command`。提议持久参数、参数哈希及资源版本包含这份身份；模型不能凭自己填写的 ID 或摘要绕过账号核对。

账号快照只使用 ID、名称、角色及已有创建/更新时间，不包含密码、联系方式或其他凭据。它是当前账号资料的 SHA-256 摘要，不是账号变更的单调版本，也不是秘密认证令牌；实际权限仍由服务端重新鉴权。

批准前重新核对目标 ID 与快照。执行事务对目标账号持有 `FOR SHARE` 锁，核对操作人当前主管权限，对任务持有行锁；业务写入完成后再核对回执中的责任人和操作人。账号不存在、同名账号对应了另一个 ID、角色或快照已变化时拒绝并要求新提议，不把旧确认转移给新账号。共享锁仅在短业务事务内持有，不跨模型调用、用户等待或文件网络读取。锁的语义参见 [MySQL 8.4 锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

System 账号模块拥有账号查询与锁，Detection 只调用 contracts 门面；Detection 拥有任务和分派身份事件，AI 继续拥有确认状态和私人提议。没有跨模块直接查询对方业务表。

## 确认策略与旧记录

新分派确认策略为 `quality-assignment-confirmation-v2`，资源版本绑定任务资料、责任人 ID/快照和可用的分派身份修订号。旧五字段 Java 构造方式仍能生成提议请求，由服务端补齐受信身份；真正执行必须带已保存的固定身份。

新代码可读取旧提议与结果；缺失 ID 显示未知，不从当前同名账号补造。旧 v1 待确认提议仍可读取、拒绝或取消；批准时因策略变化失效，需要重新生成，不自动升级原批准范围。恢复旧应用镜像能否读取新增 JSON 字段仍需兼容基线与回滚保护，不能仅凭新代码能读旧数据认定双向兼容已完成。

## V54：分派操作人和身份事件

非破坏性迁移新增任务字段：

- `assigned_by_user_id`、`assigned_by_identity_name`：实际分派操作人的稳定 ID 与名称快照。
- `assigned_to_revision`：本次选定责任人的账号快照摘要。
- `assignment_identity_revision`：任务分派身份的独立修订号，初始实际值为 0，新分派在任务行锁下递增。

另增 `detection_assignment_identity_event`，保留任务、实际版本、操作人/责任人 ID 与名称快照、账号摘要、请求编号及 UTC+8 时间，不保存分派备注、聊天或凭据。账号、任务后来删除不通过外键级联清除事件。

`DETECTION_ASSIGNMENT_BINDING_ENABLED=false` 默认关闭；启用需 V40/V54、稳定身份服务和必要业务审计。缺少前置服务或表时拒绝启用。根目录与 Detection classpath 均保存 V54 副本，没有执行任何 SQL，也不推断历史分派操作人。

启用后，分派任务、责任人 ID、操作人字段、身份事件和必要业务审计同事务保存；失败一起回滚。请求编号和实际版本有唯一约束，重复编号不产生第二次已提交身份事件。它不是对所有旧接口提供了完整的历史响应重放：原 Agent 确认仍复用原确认回执；旧业务入口遇到未知结果应先读取任务/审计，不自动再次分派。

## 人工业务表单与两套卡片

原员工账号只读目录增加 ID 与快照，仍只对当前主管开放，响应 `no-store`。目录采用有界名称候选加批量账号读取，避免每个选项各查一次完整账号；移除或角色变化的候选不作为可选员工。

检测页面、质检队列、批次追溯、工单追溯及缺陷证据页面共用 `QualityAssigneePicker`。打开分派时不把旧名称自动当作已确认身份，需从实际员工目录选择；界面显示 ID，固定账号快照，提交携带两者。Vue/React Agent 卡片同时展示旧/新责任人 ID、账号摘要、已记录分派操作人及实际分派身份版本，历史缺失显示未知。

V54 开启后还必须提交打开表单时的任务分派身份版本；陈旧或缺失版本拒绝。进度、结果、追溯 DTO 和前端轮询状态同步该值，未启用时为 null，不能显示为 0 或沿用旧缓存冒充已核实。版本冲突后需要刷新任务、重新选择账号并确认，不静默更新版本后重发。

默认关闭 V54 时，仍有服务端固定账号、重新鉴权和账号锁；旧业务客户端可以沿用名称请求，在执行时选择当时的精确账号。不能把这一兼容模式宣称为客户端早期选择也已固定 ID。最终启用后未升级的写客户端须迁移到携带 ID/快照/版本，旧读取继续保留。

截止时间的业务门面转换显式使用 UTC+8，不依赖宿主机默认时区。复核、放行、报告独立审批的授权语义保持原流程。
