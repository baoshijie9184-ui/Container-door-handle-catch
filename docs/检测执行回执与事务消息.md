# 检测执行回执与事务消息

开发分支 `java-cloud`，时间统一 UTC+8。当前为未发布实现，不能据此声明 Agent 创建、重试的完整确认闭环已完成。

## 事务边界

V42 增加命令回执、事务消息和 worker 执行回执三张表。后端在任务状态、必要审计同一事务内保存待发布事件；独立发布器按数据库时钟领取有期限的租约，网络调用不持有数据库锁。发送结果不确定时重投原事件编号和原正文，旧租约不能覆盖新领取者的状态。

worker 以 `(task_id, dispatch_id)` 为执行唯一键，同时约束事件编号。运行前先提交 `RUNNING` 回执；CPU 检测和 OSS 上传在数据库事务外进行。完成后保存完整完成事件及 SHA-256，再发布 Kafka，收到发布确认后同步提交原消息位点。完成事件允许重复投递，由后端现有任务锁、当前 dispatch 和事件编号检查去重。

已完成回执在进程重启后仍复用原完成事件，不再次检测。不同 dispatch 对应显式新执行，不复用上一次结果。正文变化、事件编号冲突、结果损坏、数据库不可用均拒绝继续推理。

## 未知结果

已开始但尚无可靠完成回执的执行不会按超时重新领取。异常时尽可能记录 `NEEDS_REVIEW`；进程突然退出可能保留 `RUNNING`，同样禁止自动重做。即使数据库完成提交的确认丢失，后续查询仍能复用实际已提交的完成结果。

等待回执时暂停该 Kafka 分区，保留未提交位点，每五秒只读核对已有完成状态。其他分区继续处理；同一分区后续消息按 Kafka 顺序等待。若原执行后来完成，则复用结果并恢复分区；重启或重平衡后仍根据 Kafka 位点及 MySQL 回执恢复等待。没有新增“清空回执并重跑”入口。重试已接通业务回执核对和两入口人工确认，创建新检测及图片完整展示仍待补齐；通过完整候选验收前不启用生产写工具。

## 配置与兼容

`compose.detection.yml` 用同一个 `DETECTION_EXECUTION_COMMANDS_ENABLED` 配置同时控制后端事务消息和 worker 回执，默认 `false`。启用前必须先在候选库执行 V42，并完成真实 Kafka、权限、确认和回滚验收；不能仅启用后端事务消息而让 worker 无持久去重。

worker 使用显式的 MySQL 主机、端口、库名及应用账号配置，不接收浏览器提供的数据库地址，不自动建表。数据库连接使用 UTC+8，事务不跨越模型、OSS 或 Kafka 调用。PyMySQL 1.1.2 固定版本，MIT 声明保存在 `deploy/worker/licenses/PyMySQL-LICENSE.txt` 并随构建上下文和镜像保留。

关闭开关保留旧版执行方式，新增表和回执不得删除。存在未核对执行时不得靠退回无回执旧 worker 来清空积压，这可能再次推理；最终发布的兼容回滚演练必须覆盖该限制。
