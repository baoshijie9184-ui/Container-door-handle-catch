# 检测模型文件登记与保留

日期：2026-10-22，UTC+8。分支：`java-cloud`。

本轮为新增实现代码，未编译、测试、构建、执行迁移、启动服务或部署。这里的检测模型指现有 ONNX 上传登记，不更换服务器已经使用的 CPU PTH 权重，也不涉及 LLM 凭证。

## 文件与 SQL 的边界

原上传异常处理直接删除目标文件；若数据库已经提交但确认丢失，这会破坏已登记模型。原删除则先删除文件，再删除数据库记录，必要审计失败时数据库可以回滚，文件不能恢复。

现在由 `ModelUploadFiles` 负责有上限的文件写入，`ModelRegistrationService` 通过独立 Spring 代理完成 SQL 登记。写文件、模型校验和再次读取 SHA-256 在数据库事务之外执行；登记模型、文件状态、模型操作日志与启用后的必要业务审计在同一事务内完成。不使用提交后的进程内回调承担持久回收责任。实现复用项目现有 Spring 事务和 JDBC，未引入执行框架；参考 [Spring 编程式事务](https://docs.spring.io/spring-framework/reference/data-access/transaction/programmatic.html) 与 [事务事件说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html)。

写入使用服务端 UUID 文件名、`CREATE_NEW`、不跟随目标符号链接，并核对父路径没有符号链接。流式校验大小和实际长度，计算 SHA-256；支持 POSIX 属性的文件系统在创建时设为 `0600`，其他文件系统沿用目录 ACL。`force(true)` 成功后登记文件就绪，模型校验结束后再次核对长度及摘要。这些检查不表示已经证明断电、磁盘故障或宿主机遭入侵时的完整恢复能力。

账号身份通过 `contracts` 的 `BusinessUserDirectory.authenticated()` 取得。System 模块只接受携带稳定用户 ID 的受信认证主体，再查询当前账号和角色，不根据客户端用户名或可能重用的账号名称推断 ID。写入、文件就绪和模型登记分别重新校验主管身份，登记时核对上传所属账号。

## V53 文件意图

`MODEL_FILE_JOURNAL_ENABLED=false` 默认关闭。启用前须完成 V53、V40 业务审计及后续验收，并启用 `OPERATIONS_AUDIT_ENABLED`；依赖的审计服务或表不存在时不能启动文件登记功能。两份 SQL 分别位于根目录 `sql/mysql` 与 Model 模块 `resources/db`，均未执行。

| 状态 | 已记录的事实 |
| --- | --- |
| RESERVED | 开始写文件前的意图及必要审计已提交；可能尚未写入、部分写入或写入回执丢失 |
| FILE_READY | 已记录写入完成时的长度及摘要，尚未记录模型登记成功 |
| REGISTERED | 文件状态、模型记录、操作日志和必要审计已在同一事务登记 |
| RETAINED | 模型登记被删除，已记录原托管文件的摘要及长度，文件保留待回收 |
| RETAINED_LEGACY | 模型登记被删除，但旧文件缺少受控上传摘要，保留位置待核对 |

意图表对账号 ID 与请求编号建立唯一约束；重复编号在再次写入前拒绝，不静默创建第二个文件或用另一份正文覆盖第一次上传。接口沿用原 Axios 请求编号，没有编号的旧调用由服务端生成并返回。编号是相关性证据，不表示所有历史模型 CRUD 已具备完整命令回执和安全重发能力。

只有模型行 INSERT 明确抛出的唯一键冲突允许在旧事务回滚后重新进行最多三次登记；不重新上传或校验。提交、连接或审计结果不明确时不重试登记，也不删除文件。进程重启不自动重放上传或补登记，保留原始状态用于核对。

开关关闭时，SQL 登记仍使用独立事务，异常不再删除上传文件，删除模型也仍保留文件；不会访问 V53 表或伪造旧文件的意图记录。此时失败文件需要另行核对，不能把页面“未启用”解释成没有遗留文件。

## 删除模型与旧入口

删除使用模型行锁并保留原有引用计数检查。启用 V53 后，在删除模型行的同一事务保存独立保留记录和必要审计；失败时一起回滚，期间不执行文件删除。旧元数据删除服务也转到相同服务代理，不绕过引用检查和保留规则。更新元数据不得领取另一个托管上传路径，或以修改路径的方式解除托管文件证据。

原 `model_operation_log` 在基础 schema 中有指向模型的级联外键，删除模型后再插入该表不能保存删除证据。删除证据由独立业务审计和 V53 保留记录承担，不声称级联删除后的操作日志仍在。上传及仍存在的模型操作日志写入失败不再被吞掉。

文件保留记录保存服务器内部位置，HTTP 查询 DTO 不返回路径、原文件名或正文。保留不是回收完成，也不是后来文件仍存在的证明。当前没有后台删除器、自动回收计时器或根据旧路径猜测删除的入口。

## 页面与只读核对

原模型列表及独立模型上传页增加“文件记录”抽屉，调用主管只读接口 `GET /api/models/file-operations`。可按请求编号查询，留空时各显示最近 50 条上传和保留记录；状态、文件编号、原模型编号、摘要、已知长度和 UTC+8 时间由白名单 DTO 提供，未知长度不显示为零。响应使用 `no-store`。

刷新与查询不重发上传、登记或删除。原上传页同时检查 HTTP 结果和业务响应码，避免 HTTP 200、业务码 500 时误报成功并清空表单。上传错误提示保留请求编号并指向文件记录，不建议直接再次上传。删除确认及成功提示明确说明只删除模型登记、文件保留待回收。

## 仍需开发和后续验收

- 明确授权后的物理回收、已引用文件与历史快照保护、未知回收结果的持久核对及账号存储配额；本次不把文件保留当作完整回收能力。

- 旧模型元数据入口的完整命令回执、版本并发、历史任务实际引用与计数一致性；原主键和名称版本唯一约束也须在真实库核对。

- V53 部署迁移/回滚编排、SQL 副本及签名核对、现有测试随新代理边界调整、审计失败回滚、磁盘写入异常、实际重启及两入口浏览器验收。
