## 本次实现的业务闭环

“质检追溯 → 报告与审批”，地址 `/#/quality/reports`。检测记录的“报告草稿”按钮可携带任务编号进入。

1. 员工对当前有权限的已完成或部分失败任务创建个人草稿，填写标题与编写意见。
2. 草稿仅本人查看、编辑；保存时读取最新任务事实，不接受客户端提交检测数量、审批角色、所有者或状态。
3. 本人提交后冻结标题、意见和检测依据，形成 `SUBMITTED` 报告版本。主管可以查看待审内容与操作记录。
4. 另一名主管填写审批意见，获取预览，再明确确认通过或驳回。主管不能审批本人提交的报告。
5. 通过后的报告可导出固定 Markdown 文件，含编写账号、提交与审批时间、审批意见、检测依据与快照摘要；每次导出写审计。
6. 驳回、撤回或通过后，本人可以创建引用旧报告的新修订草稿。旧记录和意见保持不变，修订再次提交、审批。

状态为 `DRAFT → SUBMITTED → APPROVED / REJECTED / WITHDRAWN`。撤回仅本人执行；审批仅当前有效主管执行。修订创建新报告 ID，通过 `previousReportId` 关联历史。`version` 为单份报告的修改与流转版本，并非报告系列的连续修订序号。旧 JSON 即时导出按钮改称“导出任务摘要”，与新的已审批快照入口分别呈现。

本阶段“审批通过”表示主管审核该份报告内容；报告审批不改写任务检测结果、人工复核结论、产品放行或处置状态。尚未实现公共发布、数字证书签名、多人会签或正式 PDF/Word 文档。现有任务人工复核接口仍独立存在，本次不将其当作报告审批。

## 数据与权限

报告保存稳定 `owner_user_id` 和编写账号；每次操作从系统门面读当前用户及主管角色。任务仍遵循现有“员工看本人创建或当前分派任务、主管看当前企业业务数据”。报告额外要求本人所有权，员工不能读取同事草稿或同事提交的报告，即使同样可以读取来源任务。

主管列表包含本人草稿以及已提交过的报告，不能读取其他人的私人草稿。已提交的报告允许主管查阅和审批。报告详情、审计与导出均再次校验任务范围；重新分派后，原报告所有者若不再拥有任务范围，随即失去报告读取权。列表 SQL 在分页和计数前同时应用所有权、状态、任务范围，保证总数与明细一致。

提交时保留任务事实白名单：任务与运行编号、模型及版本、图片统计、缺陷统计、复核账号/结论/时间、处置与复检状态。响应不返回对象存储 Key、内部文件路径或原始结果正文。整体任务状态计算规范化 SHA-256，提交与批准前重新核对；任务依据发生变化时拒绝旧草稿提交或旧申请批准。保存草稿更新依据，已提交申请可由本人撤回后修订。

批准要求：任务 `COMPLETED`、总图片数大于零、全部图片已处理且成功、失败数为零、人工复核 `REVIEWED`，没有待复检结论、复检标记或返工待办。批准条件由 Service 核对。任务依据变化或未完成复核的申请仍可被主管驳回并要求修订。

已通过报告导出使用提交时的历史依据；后续任务变化不改写历史内容，读取时仍检查当前访问权限。标题和意见以普通文本显示，Markdown 导出转义 HTML 与特殊标记，不将用户输入作为可执行页面。

## 确认、版本和幂等

所有写请求携带 `X-Report-Action: update`，沿用现有 CORS 来源范围。草稿创建、编辑、提交、撤回、修订和审批还需 `requestId`，后续命令需 `expectedVersion`。服务端记录 `(actor_user_id, request_id)` 及规范化参数摘要、原响应；相同请求重复返回原结果，不重复业务、审计或领域事件。相同编号不同参数返回 409。重放也检查当前身份和报告访问范围，不因存在历史结果而绕过权限。

`decision-preview` 返回 10 分钟有效的服务端确认凭证，绑定主管账号、报告版本、冻结快照、决定和审批意见。最终确认重新核对身份、权限、版本、快照、任务依据和到期时间；改变意见或决定、借用其他主管凭证、使用已消费或过期凭证均拒绝。前端先展示预览，再单次提交确认；请求失败不自动重发。页面按同一操作和参数保留请求编号以便显式重试。

事务采用 `READ_COMMITTED`，报告行锁序列化版本修改，批准时再锁任务。两名主管审批同一版本只有一项可以提交；另一项得到冲突。批准、审计、确认凭证消费、请求结果和 outbox 同事务写入，任一必需写入失败全部回滚。

新增五张表：`detection_quality_report`、`detection_report_audit`、`detection_report_command`、`detection_report_confirmation`、`detection_report_outbox`。outbox 已保存提交、撤回、通过和驳回事件及版本，当前 `PENDING` 表示尚未投递；本轮未实现 Kafka 发送器或通知消费，不能声称事件已发送。审计记录创建、修改、状态流转与导出。普通 SHA-256 可发现内容与摘要不一致，不能描述为绝对防篡改审计或数字签名。

## API 和迁移

前缀 `/api/detection/reports`：

| 接口 | 行为 |
| --- | --- |
| `GET /` | 按角色、所有权及任务范围分页 |
| `POST /` | 创建私人草稿 |
| `GET /{id}`、`GET /{id}/audit` | 读取授权报告及最近 100 条操作记录 |
| `PUT /{id}` | 本人编辑草稿并刷新依据 |
| `POST /{id}/submit`、`POST /{id}/withdraw` | 本人提交或撤回 |
| `POST /{id}/revise` | 由已结束版本创建新修订草稿 |
| `POST /{id}/decision-preview`、`POST /{id}/decision` | 主管预览、确认审批 |
| `POST /{id}/export` | 下载已审批 Markdown，响应 `Cache-Control: no-store`，写导出审计 |

参数错误 400，权限拒绝 403，资源不可见 404，版本/确认/依据冲突 409，预览过多 429。数据库异常不直接暴露给用户。审批、确认的接口主体及校验以 DTO 与 Service 为准，不接受聊天文字当作批准。

新开发库在已有 schema 后执行 [V21](../sql/mysql/migration-V21-quality-report-approval.sql)，classpath 副本位于 App 模块；本机已重复执行验证，只增加表，不修改原任务、用户密码或角色。

脚本只操作 `.env` 所指定的本机 `doorhandledb`，省略 `--apply` 只检查。启动就绪检查增加五张报告表，统一启动入口不自动迁移或创建报告。部署先备份并核对目标库；MySQL DDL 非完整事务，可重复执行恢复中断；回退应用时保留新增表和历史审批，不自动删数据。
