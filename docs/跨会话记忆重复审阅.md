# 跨会话记忆重复审阅

2026-10-18，UTC+8，`java-cloud`。复用 Mem0、Chroma、现有私人记忆页和 V26 MySQL 审计，不引入另一个 Agent 执行框架。代码和本地验证已完成；统一云端发布、真实长期提炼质量及完整生产验收仍待完成。

## 使用与权限

本人记忆卡片的“查找相似”先读取当前正文与治理版本，点击“开始分析”才调用记忆模型。主站和独立 Agent UI 通过既有“个人记忆”入口共用这个页面。关闭助手读取设置后不能新发起 AI 对比，仍可查看本人历史或处理已经生成的建议。

页面并列显示原记忆、候选、来源会话和关系建议：可能重复、可能矛盾、相关但有区别、不同信息或需要人工判断。文本作为纯文本显示，不能执行其中 HTML、脚本或指令。用户选择保留原记忆并停用候选、保留候选并停用原记忆，或保留两条；必须先预览，再明确确认。模型没有处理记忆的工具或授权。

停用只影响后续长期记忆检索，保留正文、来源会话、原有效期和自动清理同意状态；不是合并、覆盖或物理删除。可在既有“有效期与停用”恢复，但原有效期仍须核对。错误正文仍通过既有编辑预览确认纠正。保留两条会记录这对正文与治理版本，后续新分析不再反复展示同一版本组合，任一条内容或治理版本变化后可以再次出现。

员工和主管都只管理自己的私人记忆。外部接口不接受指定账号，内部桥接从 Java 的登录身份获得 `user_id` 与固定应用编号；主管权限不能扩大到其他账号记忆。

## 检索、模型与预算

手动分析使用 Chroma 已保存向量，不额外调用 Embedding。原记录与候选重新验证所属账号、应用、正文和治理版本；原记忆最多 4000 字，候选只接纳 4000 字以内且仍有效的条目。读取本人账号最多 20 条向量近邻，重算余弦，至少 0.65 才进入候选，最终最多展示 5 条。没有候选只表示本次有限近邻范围未找到，不证明整个账号无重复。

完全相同的正文直接标记为可能重复。其余候选用一次 Mem0 已配置模型请求判断，输出仅允许候选临时编号与固定标签，检查缺失、重复、多余编号和未知标签。模型输入是记忆数据，不具有业务授权。向量相似度不是准确率或删除依据；同实体下数值、时间、范围、否定词和独立新增要求均须区分。

模型失败、超时或返回格式不可核对时保留候选，展示“模型暂未给出可核对的判断”，不改成没有重复。自动写入与手动审阅共用单个有界工作线程和全局写槽；忙碌时新任务明确返回未开始，读取列表和历史仍可执行。没有增加并发调用或自动重试。首次只短暂等待，202 保留为处理中，前端后续只读轮询；关闭弹窗不会假装取消供应商请求。

| 配置 | 默认与范围 |
| --- | --- |
| `MEM0_DUPLICATE_REVIEW_ENABLED` | `true`，关闭后禁止新分析，保留本人历史读取及已生成建议的明确确认 |
| `MEM0_DUPLICATE_REVIEW_TIMEOUT_SECONDS` | 30 秒，允许 1–60 秒；手动审阅单次 SDK 请求等待上限 |
| `MEM0_EXTRACTION_TIMEOUT_SECONDS` | 自动提炼模型默认 30 秒，后续真实链路验证新增；手动审阅结束恢复原客户端配置 |
| `MEM0_PROVIDER_TIMEOUT_SECONDS` | Embedding 默认 15 秒，不因提炼或审阅而延长 |

`with_options` 共享原 HTTP 传输，审阅结束恢复原客户端，不关闭共享连接池。请求超时不证明供应商停止计算，也不将 SDK 读取等待上限声称为强制供应商 Token/计费上限。百炼的 `kimi-k3` 是仅思考模型，不能以关闭思考规避等待；依据 [百炼 Kimi 文档](https://help.aliyun.com/zh/model-studio/kimi-api)。本轮没有更换默认模型或密钥。

页面展示配置模型名、SDK 调用耗时及供应商报告的输入、输出、总 Token。原生响应回调捕获用量并恢复原回调；没有供应商值时保持 null/未知，供应商报告 0 才显示 0。历史与重复读取不再次调用模型或累计 Token。配置名不证明上游实际路由，耗时包含等待与传输，不等于首响应时间、纯推理时间或费用账单。

自动提炼仍通过原生 `add` 保存当前来源会话；只在该提炼线程和匹配账号/应用的向量搜索内去除 `run_id` 过滤，使已有同账号记忆可跨会话参与去重。普通会话检索、其他账号及其他线程不扩展范围。原生近邻及哈希去重是有限范围，不能保证全库语义唯一，也不自动纠正错误记忆。

## 持久化、确认与异常

私有桥接 SQLite 共用原持久卷、进程锁、WAL 与完整同步设置，新增分析、决定和保留两条的版本组合表。只保存编号、摘要、标签、状态、用量与时间，不复制正文、向量或供应商原始响应。读取历史时重新从受权原记忆投影正文；已变化、停用、到期、移除的记录标为失效，拒绝沿用旧建议。

分析登记先持久化再排入原执行器；执行器拒绝会将已登记记录改为失败。重启后仅将原 RUNNING 标为 INTERRUPTED，不自动重做。本人最近 20 条历史支持刷新后继续读取；这只是读取上限，不是物理保留或删除策略，长期审计容量仍需后续治理。

确认请求同时携带独立决定编号、原审阅版本、候选编号和明确确认。Java 先写 V26 MySQL 审计，桥接再核对原记忆与候选的正文摘要及治理版本。治理停用、决定回执和审阅版本递增在同一 SQLite 事务；失败回滚。相同请求只返回原回执，换内容复用编号或陈旧版本返回 409。预先审计不可用时不调用远程处理。

HTTP 结果或 Java 完成审计未知时阻止继续提交，读取原分析核对匹配的决定编号、版本和指纹，再收敛 MySQL 审计，不自动重新停用。已经完成的决定保留原执行证据。手动停用仍是单桥接进程协调，不能称为多副本分布式事务。

| 本人 HTTP 接口 | 用途 |
| --- | --- |
| `GET /api/agent/memories/reviews` | 最近分析，不调用模型 |
| `GET /api/agent/memories/reviews/{id}` | 重新鉴权读取，核对决定回执 |
| `POST /api/agent/memories/{sourceId}/reviews` | 带正文及治理版本开始只读分析，200/202 |
| `POST /api/agent/memories/reviews/{id}/resolve` | 预览确认后的版本化治理决定 |

所有响应 `Cache-Control: no-store`。外部接口不暴露 SDK 状态、服务器路径、其他账号或密钥。无新增 MySQL 迁移；继续使用记忆协议 2，实际持久治理效应仍为既有 EXCLUDED 规则，旧协议 2 桥接忽略新分析元数据不会撤销停用。协议回滚保护见 [跨版本保护](Mem0跨版本回滚兼容保护.md)。
