# 微服务开发

**这是后续设计，不是当前部署。** 先在 `java-cloud` 完成 [单体开发](../monolith/README.md) 和功能验收。用户确认开始拆分之后，才创建或恢复一条微服务开发分支；在此之前，不增加 Nacos、Seata 等微服务专属组件，不启动历史三机或 15 机方案。

## 拆分顺序

1. **先定业务边界。** 以 [第三个工作技术方案](第三个工作-技术方案.md) 的五个领域服务加独立 Python 推理为设计起点。先写清每个领域拥有的数据、允许对外查询或修改的契约，以及来自用户的身份和操作编号；不按页面个数拆服务。
2. **先让数据归属清楚，再接分布式事务。** 同一领域仍优先使用 MySQL 本地事务；其他服务通过 API 或事件取得事实，不直连另一服务的业务表。跨域写入才选择适合该流程的 Seata 方式、事务消息或业务补偿，并验证重复命令、超时未知结果和失败恢复。
3. **只引入当前切片需要的设施。** 业务路由、注册配置、RPC、异步任务、向量与观测按技术方案分层选型。先做一个端到端用例，再按实测并发、积压和资源争用决定部署规模。缓存和搜索结果不取代业务权威状态。
4. **最后定义上线与恢复。** 在创建新环境之前确定数据迁移、身份一致性、同一固定版本的验收和故障回退。原单体的 Jenkins、ECS 与数据库门禁不能直接套用到新拓扑或绕过。

## 与 Agent 的关系

Agent 调用受授权的领域接口，不持有跨域写库权限。先保留 [Agent 开发](../agent/README.md) 的身份、审批、工具回执和重放边界，再把进程内实现替换成版本化服务契约。容量报价和部署草案只用于后续评估，不是采购依据。

分支管理、整合与统一验收遵循 [开发总规则](../开发规则.md)。
