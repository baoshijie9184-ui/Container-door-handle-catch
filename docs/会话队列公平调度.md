# 会话队列公平调度

2026-10-18，UTC+8，`java-cloud`。沿用现有 App 会话消息队列和 AgentScope 执行门面，不新增执行框架。

## 问题与行为

原调度器只读取全局最早的 32 条待处理消息。每账号上限为 16 条，两个忙碌账号各积压 16 条后，第三个空闲账号的消息排在第 33 条，后续调度仍重复扫描前 32 条，可能一直无法开始。原按全局编号优先也会让一个有多条消息的账号连续占用领取机会。

现按稳定账号编号轮转：每次最多读取 32 个待处理账号，每账号最多检查 16 条消息，账号内仍按消息编号顺序检查。成功领取一个输入后即让出本次调度；下次从后一个账号继续，忙碌账号不能遮住其他账号。账号超过 32 个时分批前进，扫描末尾回到下一轮。

每轮固定当时已入队的最大账号编号，新加入的账号在后续轮次加入，避免持续注册的新账号让调度永远不能回到前面的账号。该游标只控制扫描顺序，不保存业务执行状态；重启可从新一轮开始。MySQL 原有账号锁、会话活动唯一约束、版本化状态和审计继续决定真正的领取者。

保持现有语义：暂停/等待计划的会话不被强制执行，权限和角色在领取及执行时重新核对，已 STARTED 的消息不会因重启而重放，未知失败不自动重试。仍使用两个有界后台执行线程，空闲账号不存在时同一账号的独立会话可使用可用执行资源。

组件停机时先停止调度，后台执行线程最多等待五秒完成已接纳的短任务及事务清理，超过预算再发出中断；调度线程有独立的两秒退出预算。该预算不保证长模型/工具调用完成，也不把中断时的未知业务结果视为未执行，继续沿用检查点和人工核对机制。

## 数据库与上线

V39 只新增 `agent_conversation_input(status,user_id,id)` 索引，支持待处理账号范围读取与账号内顺序领取。根目录 `sql/mysql/` 与 App `src/main/resources/db/` 两份 SQL 保持一致。迁移不修改消息、审批或执行证据，应用回滚时保留索引。

最终统一发布前，在备份后检查索引是否已存在；未存在时执行一次 V39。索引创建结果不明时先查询 `SHOW INDEX`，不能盲目重复执行。该版本不会在启动时自动修改数据库。

## 验证状态与边界

原实现的三个新增用例均复现失败：两账号 32 条忙碌消息阻挡第三账号、连续领取偏向一个账号、超过 32 个忙碌账号后无法前进。失败记录保存在 `work/queue-fairness-before.log` 与 `work/queue-fairness-before-report.xml`。

修复并补齐新账号轮次、优雅停机边界后，完整 Maven clean verify 共 851 项，789 通过、62 可选联调跳过，零失败/错误，13 模块成功。首次原生 MySQL 为 25/27：三秒观察预算不足，且查询计划用例把特定索引名称当作唯一答案。改用同账号千条历史及实际范围/排序/扫描量检查，原生观察预算单独设置为十五秒，业务执行超时未修改；失败报告保留。

最终显式 MySQL 8.4.11 共 28 项全部通过，包含原有权限、审计、跨实例领取竞争、暂停/重启、配额、新轮转与有界停机。原生检查使用受控的用户目录、会话和执行回调，不调用真实模型；不能记为生产 HTTP/真实角色目录或容量验收。待处理账号查询实际使用 V39 新索引，账号内查询使用既有 status/id 索引，两者均无 filesort，估算扫描 16 行；未强制索引或关闭优化器。五秒收尾消除了先前测试中事务清理遇到已关闭连接的告警，最终运行零 WARN/ERROR。

只有随机专属测试库配置才能启用原生夹具。两个专属数据库、短期账号、SSH 隧道及复制的连接配置均已清理，未修改应用业务表。证据为 `work/queue-fairness-full-maven.log`、`work/queue-fairness-full-evidence.json`、`work/queue-fairness-native-final-mysql.log`、`work/queue-fairness-native-final-report.xml`、`work/queue-fairness-query-plans.json` 和对应清理回执。

这不是生产多用户容量或多副本全局公平性保证。轮转顺序属于当前单体进程，跨实例仍使用数据库领取保护，但没有引入全局公平调度协调；真实模型耗时、长任务等待、生产负载和两个入口仍需后续验收。Jenkins #25 验证的是本轮队列改动之前的提交，不能用其结果证明本轮 Java 改动已经发布或验收。
