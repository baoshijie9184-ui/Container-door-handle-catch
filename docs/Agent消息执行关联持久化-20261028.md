# Agent 消息与执行关联持久化

纯文本回复原先只通过浏览器内存保存工具运行编号，整页刷新后执行组可能消失。本轮新增独立的消息与运行关联表，使已有会话读取接口可以返回准确的 `runId`。React 和 Vue 已使用该字段，不需要改动聊天路由、模型调用或前端技术栈。

## 实现与边界

- `MessageExecutionLinks` 在助手消息保存后，使用服务端实际返回的消息编号、运行编号关联两者。SQL 同时核对账号、会话、助手角色、消息类型及顶层运行入口，只接受已结束或已保存等待回复的运行。
- 一条消息对应一个运行，一个运行最多关联一条已保存回复。重复处理不会覆盖原关联。
- `ChatSessionServiceImpl` 在现有所有权检查后，给返回的可见历史消息批量补充 `runId`，每批最多 200 个消息编号。关联读取再次核对账号、会话、消息和运行归属，不逐条查询工具气泡。
- 不修改历史消息正文、类型、审批状态或业务结果，不根据文本、时间或默认模型反推运行编号。旧历史没有明确关联时不回填。
- 未运行迁移或数据库暂不可用时，记录脱敏服务日志并暂停关联查询 60 秒，聊天正文仍可保存和读取。恢复条件满足后自动重试。此时没有持久化关联的新纯文本消息仍沿用浏览器内存展示，整页刷新后的恢复能力会受限。
- 原工具记录接口继续检查访问权限；这里增加的是消息关联元数据，不是额外的数据访问授权。

## 迁移及兼容

归档脚本：`sql/mysql/migration-V66-chat-message-execution.sql`。

运行时副本：`doorhandle-module-app/src/main/resources/db/migration-V66-chat-message-execution.sql`。

V66 只幂等创建 `agent_message_execution`，不修改 `chat_message` 原表，不删除或回填旧历史。表采用递增主键，消息与运行分别唯一，账号、会话、消息编号组成批量读取索引；字符串标识沿用现有运行日志的区分大小写规则。

部署时需要先启用既有运行日志功能，并在 V16 的基础上显式执行 V66，正常聊天产生的新回复才会获得持久关联。classpath 副本不会在启动时自动执行。本轮没有修改 Jenkins、Docker、ECS 配置，也没有执行云端迁移、提交、推送或发布。

回退到旧应用版本时可保留新表，旧代码不会读取它，不需要删除历史关联。未迁移的环境继续使用原有会话能力。

## 验证

数据库测试使用项目已有 H2 的 MySQL 兼容模式，测试时仅去除 H2 不支持的存储引擎与排序规则声明。未进行真实 MySQL 迁移演练；这些结果不代表 ECS 已应用新表或已经完成云端验收。
