# 第一版核心业务表草案（已撤回）

当前候选见 [29 表业务模型](compact-schema-proposal.md) 与 [核心 13 表实现](compact-core12.md)。以下九表、旧类型名和列数仅保留为历史依据，不能据此生成现行 DDL。

2026-11-05 更新：本文件保留第一版设计依据，以下九表清单不再作为最终方案。历史汇总、图片资产/成员/上传、审批报告/日报/投影三组混合设计已进入重设，见 [核心边界复审](review-core-boundaries.md)。最终表数以重新划分职责后的结果为准，30 仅为上限。

这部分把账号、员工、设备、检测模型、检测任务、图片和报告归入九张实体表。它是全项目三十张表方案的一部分；通用操作、审计、协调状态和 Agent 数据由另外二十一张表承担。当前文件是待 ECS 验证的 MySQL 8.4 建表源码，生产数据库尚未改成该结构。

| 表 | 用途与保留边界 |
| --- | --- |
| `users` | 登录身份、角色和明确的员工绑定。密码与角色不随员工在岗状态变化。绑定版本、是否曾有绑定记录保留在账号行中。 |
| `employee` | 员工档案和部门关系。员工可以没有登录账号，不根据姓名自动合并人员。 |
| `organization_department` | 部门主数据，保留现有编号和名称唯一规则。 |
| `device_management` | 设备档案、当前使用员工、心跳与采集状态。历次使用、告警及处理过程由通用操作记录保留。 |
| `model_management` | 检测模型版本、发布状态、评估指标和训练事实。缺失的实测数据仍为空值；模型文件的上传和保留记录进入 `agent_document` 的模型文件类型。 |
| `detection_task` | `TASK` 保存当前检测任务；`LEGACY_SUMMARY` 保存原 `image_detection_data` 的历史汇总。历史数量、原始日期和旧编号都有独立列，不补造原图、任务状态或审批事实。 |
| `detection_work_unit` | 保留工作单元、负责人、图片数量、分派与完成进度，独立于具体检测运行。旧字符串身份值不直接解释成账号数字编号。 |
| `detection_image` | `CANONICAL` 是指纹登记，`WORK_UNIT` 是图片在工作单元中的成员记录，`TRANSFER` 是单次对象上传凭据。一个内容哈希可以对应多次合法使用和上传。 |
| `quality_document` | `QUALITY_REPORT` 保存质检草稿及独立审批，`DAILY_DIGEST` 保存日报执行与快照，`REPORT_STATE` 保存消息消费的只读投影。消费投影不能提供审批或账号归属依据。 |

建表入口为 `sql/mysql/compact/baseline/10-core.sql`，恰有九条 `CREATE TABLE`，不使用 `IF NOT EXISTS`、兼容视图或种子业务数据。它只用于显式指定的新空库。必须在全部 baseline 文件创建完毕后应用经过审查的外键关系；关系草稿位于 `work/schema-reduction-20261105/core-relations.sql`，尚未作为正式部署脚本执行。

查询和权限判断仍使用可索引的结构化列。JSON 只保留原有检测结果、证据和报告快照，账号、角色、状态、版本、数量、时间、任务标识、调度租约等不藏入通用 JSON。旧文本列显式保留原有排序规则；新的机器标识和类型标识使用二进制比较。变更排序规则的列必须在迁移前核对大小写及唯一值差异。

图片表采用有条件的唯一键：只有指纹登记要求哈希唯一，工作单元成员仍按原图片编号唯一，上传仍按原命令与图片序号、文件编号唯一。上传的对象 key 保留原二进制比较列，不与原指纹表的文本比较规则混用。可选的指纹关联必须有准确哈希依据；没有原始关联时保留空值。

上传记录通过 `(creation_job_id, creation_job_namespace, creation_job_kind)` 只关联 `DETECTION / DETECTION_CREATION`。日报通过对应三列只关联 `QUALITY / DIGEST_SCHEDULE`。数据库中的 CHECK 与复合外键共同限制记录类型，不能只凭通用操作编号跨类型关联。CHECK 中的必填条件显式检查 `IS NOT NULL`，避免 SQL 的空值语义放过不完整记录。

旧表的自增编号可能重复。保留现有主实体编号，并为合并后的其他类型分配独立主键；原编号与来源单独保存，用于回查和逐条验证。图片凭据原来包含无符号 BIGINT 编号，因此旧编号列使用 `DECIMAL(20,0)`，避免在合并时截断。报告状态原主键是报告字符串编号，继续由类型和报告编号唯一确定，不捏造原数字编号。

账号绑定的独立表合并后，`binding_history_present` 从旧记录是否存在回填，包括“员工为空、版本为零”的历史记录。真正绑定或解绑会保持该标志为真，无操作重试不制造历史。清退旧表前，还必须安装并验证等效账号删除保护，禁止删除存在绑定历史的账号，也禁止把该标志从真改回假。当前只补齐标志及持久层，最终数据库删除保护尚待总迁移脚本实施。

逐列依据在 `work/schema-reduction-20261105/core-column-map.json`。`image_detection_data` 已取得 2026 年 10 月 14 日真实备份中的十六列 DDL，历史汇总数、路径、日期和 `DECIMAL(5,2)` 漏检率按此保留；这份旧备份不能证明当前线上表没有后续改动。迁移前须取得当前 `SHOW CREATE TABLE`，确认历史恢复后路径空值规则和其他字段差异。其他表目前也只是仓库定义与迁移文本的静态还原，不能代替线上结构证明。

所有来源行都必须经过完整复制、旧编号核对、内容摘要核对和约束核对。遇到孤儿关系、原有值不符合新 CHECK、旧字段没有对应去向时应停止该迁移步骤并修正设计，不能过滤行后把数量对齐宣称成功。新旧表并存只用于迁移和回滚阶段；最终总表数检查需在旧结构清退之后进行。
