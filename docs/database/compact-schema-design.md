# 不超过 30 张表的数据库重构

当前阶段：采用 [29 表业务模型候选](compact-schema-proposal.md) 继续源码实现，保留独立重复图片复查工单。第一版 30 表草案已撤回；下方清单仅作历史审查，不是当前建库清单。当前权威候选是 `compact-schema-contract.json` 和 baseline DDL，最终实际交付表数仍未验证。尚未完成 ECS 建库、数据迁移和应用验收。

## 交付标准

本次重新设计当前模块化单体的 MySQL 业务库。最终活动业务库至多 30 张实际表，计数包含审计、操作回执、队列、额度和协调状态。旧表视图、运行时 SQL 改写、把旧表留在另一个活动库，都不能替代结构和代码的改造。离线备份独立保存，用于恢复，不作为应用查询来源。

企业仍为中国铁路集装箱公司，单企业、多角色、多用户。保留独立账号、员工和组织身份，不根据相同姓名自动绑定账号。模型权限延续既有规则；设置个人额度的用户才按个人额度扣减，并保留额度申请和主管审批。

30 张表是上限。表的保留依据是独立生命周期、查询关系和事务约束；数量变化必须重新核对全部功能。合并后代码必须直接访问新结构，不能保留 131 套旧表写入接口。

## 合并后必须保持的行为

同一实体的一对一附属数据进入实体自身，例如消息的执行关联和附件切点。数据须按原账号、原消息和原会话匹配，无法匹配时迁移停止并保留原记录，不能猜测归属。

操作回执、审计事件和当前状态的生命周期不同。操作回执保留请求身份和执行结果，审计事件只追加，当前状态通过版本或锁修改。删会话不能释放已经使用的分支请求编号；原分支被删除后重复请求仍须按原回执处理。

公共表的类型是有限集合，每种类型保留必要字段约束。账号、资源、状态、请求编号、版本、金额或 token 数、时间、租约与 fencing 标识使用明确字段；原有结构化正文和不可变快照可以继续使用 JSON/TEXT。不得把完整旧行塞进 JSON 后声称完成领域设计。

不同资源的账号锁保持不同命名空间。工作区操作不能因此阻塞同账号的所有业务；相同业务范围的多实例写入必须使用同一数据库事务和实际连接持有的行锁。

历史累计数据保留独立来源和原数值，不伪造图片关联，不与新检测明细重复求和。日报、普通报告和消费状态的独立唯一性与更新规则也要保留。

## 构建、迁移和验收

`script/schema/build_compact_schema.py` 只读取 SQL 并构建源码制品：核对真实建表语句、表名、主键、外键目标和类型，不连接数据库。输出明确标注尚未执行 MySQL。

`script/schema/inspect_compact_schema.py` 只允许在核验身份后的 ECS 上读取实际目录。它要求完整的业务库读取权限，核对所有活动业务库中的实际对象数和名称；只有该项通过仍不能代替功能、数据和回滚验收。

完整验收包括：在空库建立完整结构；把当前业务数据恢复到隔离来源库并逐行迁移核对；应用直接连接新结构运行；验证权限、额度、审批、幂等、并发、工作恢复、历史统计和文件读取；验证迁移后发生新写入时的恢复方案；最后切换并读取实际表清单。验证使用 ECS，结束后读取实际 `Stopped / StopCharging` 状态。

现有 001—004 等展开/复制脚本是开发过程中的局部迁移片段，不构成当前 29 表候选的完整迁移或生产切换方案。复查工单专表及其复制边界见 [独立复查工单](compact-duplicate-ticket.md)。目标表结构文件、代码、数据迁移和验收都完成后才能报告整体完成。

## 与后续分布式部署的关系

本版约束当前单体业务模型的实际表数。数据库复制副本承载相同结构；以后如果微服务各自新增公共表副本或独立业务表，必须按各活动业务库重新计数，不能只计算表模板。当前设计不自动证明服务之间的事务、权限边界或三节点高可用已经实现。
