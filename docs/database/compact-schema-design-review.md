2026-11-05 的历史复审记录。用户要求的是实际业务表不超过 30 张，而不是恰好 30 张。第一版按 9 + 17 + 4 固定表数分配职责，导致部分表只是旧表字段的并集，已撤回。下文记录当时的设计判断；当前候选为 29 张、源码实现中但未验证，ECS 业务库未因本地修改发生变化。

现行设计见 [29 表业务模型候选](compact-schema-proposal.md)：复用操作协议和内容版本协议，同时保留独立复查工单。目前已有对应候选 DDL 和部分适配源码，尚未完成整库迁移和 ECS 验收。

第一次撤回时，contract 曾标记为 `REQUIRES_DOMAIN_REDESIGN`，入口拒绝据此构建或验收。旧清单已移到 `withdrawn/compact-schema-contract-30.json`；当前 contract 为 `DEVELOPING_COMPACT29_NOT_VERIFIED`，仅表示可继续实现的源码候选，不表示实际数据库已变更或验收通过。

## 已确认的问题

| 第一版做法 | 代码和存储语义 | 修订决定 |
| --- | --- | --- |
| `operation_job` 收纳设备告警、设备使用、定时计划、同步回执、异步执行 | 告警有确认和解决状态；使用记录有借用起止；计划会反复产生执行；回执用于请求重放；队列需要领取和租约。这些不是同一种实体 | 撤回逐列拼接。公共层只统一真正相同的幂等、调度执行、审计和协调机制；业务状态由所属领域管理 |
| 历史累计记录并入 `detection_task` | 历史记录没有完整任务身份和图片明细，不能参加任务分派、重试、权限查询或作为新检测数重复累计 | 不再默认把历史记录伪装成任务，重新确定独立统计存储及追溯方式 |
| 指纹登记、工单图片和导入凭据并入 `detection_image` | 同一内容可以有多次导入和多次工单使用；内容唯一性、业务成员关系、传输重试的基数和生命周期不同 | 区分内容资产、业务引用和传输状态，再决定哪些可复用现有存储 |
| 质检报告、日报执行、消费投影并入 `quality_document` | 审批报告有人工审核；日报执行有计划和租约；消息消费状态是投影，没有审批权威性 | 报告保留业务身份；计划与执行分开处理；投影不能代替报告授权或审批结果 |
| 输入队列并入 `chat_message` | 待处理输入可以独立于聊天历史存在，删除会话时不能套用历史消息的级联删除规则 | 输入按持久队列处理，已发送消息只保存消息及真正的一对一附属信息 |
| 模型文件保留记录并入 Agent 文档，并考虑指向模型的级联关系 | 文件清理凭据可能在模型删除后仍然需要保留 | 文件身份、内容版本和清理任务分别建模，不以同为“文件”作为合并理由 |

这些问题不能靠给每种旧记录增加一个 `kind` 值解决，也不能通过把完整旧行搬进 JSON 来规避。

## 仍有依据的简化

- 账号的当前员工绑定是账号的一对一状态，可以放进账号；员工可独立于账号存在，员工档案不能因此并入账号。绑定并发版本、历史审计和删除规则须保留。
- 消息的执行关联、消息对应的附件快照，以及运行的最终回答引用结果，可以归入各自主记录；删除主记录后的证据保留必须有明确规则。
- 多套仅含账号键的事务锁可以使用带业务命名空间的协调记录；不同命名空间仍须独立竞争，不能把所有业务锁合成一把账号总锁。
- 审计可统一事件外壳，但用于查询、去重、顺序和归属的字段仍需明确列和索引；不可变详情可以采用有版本的结构化内容。

## 每个候选表必须回答的问题

1. 代表什么实体、关系、历史事实或可重建状态；谁拥有它。
2. 是否有独立主键、生命周期和权限边界，删除其他对象后是否继续存在。
3. 实际列表、关联、排序、统计和定时扫描使用哪些字段；需要什么索引。
4. 哪些数据一起提交，哪些操作需要唯一键、行锁、乐观版本或领取令牌。
5. 哪些内容是稳定字段、可变正文、不可变快照或服务器上的文件。JSON 不能吞掉权限、额度、外键、幂等和调度条件。
6. 与现有数据的关系能否无损迁移，尤其历史 ID、原数值、空值、证据和已删除资源的回执。

先回答这些问题，消除重复状态和无意义附表，再计算表数。若超过上限，重新审视可复用机制和领域模型，不为压低数字强行混合实体；若低于上限，也不补表凑数。空表不能单凭当前没有记录就删除，能否移除要以功能和调用证据为依据。
