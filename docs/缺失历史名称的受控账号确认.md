# 缺失历史名称的受控账号确认

2026-10-22 UTC+8，分支 `java-cloud`。本轮仅修改和阅读源码，未编译、测试、构建、执行迁移、运行检查器、Jenkins 或云端操作。新开关默认关闭，不能据此标记候选或生产验收完成。

## 处理范围

任务原创建人、责任人、复核人、处置人或返工人名称缺失时，不再只能永久保留待映射。主管可以核实原始业务资料，明确选择目标账号、填写资料编号，并逐条确认归属。没有足够资料的记录仍保留待映射，不按姓名、部门、相似文本或当前账号推断。

资料编号是主管声明的核对依据，系统只保存编号，不自动下载外部资料，也不宣称已经独立验证其真实性。编号限制长度和字符，不接受路径、URL、正文或凭证。名称缺失不能用“已核实改名关联”替代原始资料核实。

原业务名称、冻结报告和历史审计正文不改写。NULL、空字符串及空白文本保留原值；新身份快照保存规范化后的原名称，授权额外核对原始值与确认凭据。后续实际操作仍记录当时真实操作账号。

## 确认、持久化与回执

沿用 `/api/detection/identity/preview`、`apply`、`commands/{request}` 和批次页面。普通回填继续使用 v2 内容摘要；包含缺失名称的请求增加 `missingNames` 逐条确认清单，对应 `identity-map-v3`，绑定任务、职责、原快照、目标账号及版本、资料编号和确认标志。不能把其他任务的依据套用过来。

确认事务重新鉴权主管、锁定控制修订、目标账号及任务。任务快照包含原始 NULL 与空字符串差别，任一目标资料或任务状态变更都要求重新预览。V61 的 `detection_identity_missing_name_evidence` 与 V55 批次、稳定 ID、来源事件、必要审计及命令回执一起提交；失败全部回滚，不自动激活授权模式。

相同编号和内容读取原结果，同号不同内容拒绝。未知提交结果只读核对原编号，不自动生成另一批映射。v3 回执还核对确认数量、资料记录与映射明细的一致性；页面可查看原值类型及资料编号。刷新后读取回执，不恢复旧确认授权。原有 v2 批次继续可读。

## 授权与失效

缺失名称不能作为普通名称匹配。仅当前来源指针、来源事件、主管批次、逐条映射和 V61 凭据一致时，才允许相应稳定 ID 参与原授权策略；即使来源服务处于 COLLECTING，也不能跳过这一凭据链。

原业务名称从 NULL 变为空串、被补写或指向另一来源，原确认不再匹配。后续实际创建、分派或人工操作更新来源指针。普通业务同步保留仍匹配的确认；重试检测清空复核/处置人、返工提交清空处置人时，显式撤销相关 ID 与来源，不能因为原字段本就为空而保留旧确认。

返工清空采用明确写 NULL 的 mapper，避免 `updateById` 默认跳过空值而残留原处置记录。上述业务重置和身份撤销在同一业务事务内。

历史核对摘要可识别有效的缺失名称确认；账号失效、来源或快照不一致仍列出差异。必要创建人、责任人映射及账号检查未完成时，原授权激活入口继续拒绝切换。

## 接入和兼容

- `DETECTION_IDENTITY_MISSING_NAME_REVIEW_ENABLED=false`，依赖 V40/V55/V56/V61、稳定身份、回填、来源与必要审计服务。
- 后端 `io.doorhandle.identity-evidence` 声明为 2，原来源协议 1 仍可读。
- 发布守卫考虑开关、持久凭据、来源事件及单调 pin；产生新确认后禁止关闭兼容读取或回滚到协议 1。首次启用必须先有独立兼容恢复基线。
- V61 两份 SQL 分别位于根迁移目录和 Detection classpath，不回填、不改写旧名称、不自动开启功能。
- 管理能力属于主站企业主管页面，独立 Agent 入口继续复用现有管理导航；员工、聊天工具和普通提问回答不能授予映射权限。

完整业务调用路径清单、迁移类型/约束/索引签名、首次兼容基线，以及并发、权限、重复请求、回滚和浏览器验收仍待完成。其他四类单体功能缺口继续保留。
