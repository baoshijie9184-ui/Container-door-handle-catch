## 2. 先用内网 SSH，不增加公网入口

```text
Windows：现有 Jenkins / 本地构建 / 证据保全
                  |
             SSH / SCP（22）
                  |
Linux：10.22.0.145
  ├─ 隔离 CI：独立容器、网络、数据库和本轮报告
  └─ 长期单体：Nginx、后端及所需中间件
                  |
            按需访问 OSS / 模型 API
```

- 两端的 `/14` 地址配置均落在 `10.20.0.0/14`。这说明地址范围相同，不保证校园所有 AP、网口都允许互访。
- 恢复开发时先验证 TCP 22 和严格主机密钥校验下的 SSH 登录。若同一校园网接入仍不可达，优先换到已知可互访的接入路径，不关闭防火墙、不新增公网入口。
- 向网管确认 Linux 能否获得 DHCP 地址保留或稳定主机名；不要自行随便指定静态 IP。IP 变化时核对目标主机密钥与身份，再更新私有连接配置。
- Linux 应在批准的开发或验收窗口保持开机、网络稳定。只有选用 Jenkins 验收时，才需要对应控制器和执行节点在线。是否调整实验室设备休眠策略由主机负责人确认。

### 端口只开到需要的位置

- Linux SSH：`22`，供已批准的管理来源访问。
- 单体网页：沿用 Compose 默认 `127.0.0.1:8088`，通过 SSH 隧道在 Windows 访问。
- MySQL、Redis、Kafka、Qdrant、Mem0、AI 网关和 MCP 控制端只接 Docker 项目私网，不发布校园网端口。
- 可选监控入口仍绑定 Linux 回环：Prometheus `19090`、Alertmanager `19093`；Langfuse 启用时为 `13000`。需要查看时单独转发，不直接开放给全校。
- 不开放无 TLS 的 Docker TCP API，不为排障关闭整机防火墙。修改 SSH 或防火墙前保留本机控制台和恢复通道。

实验室单体已在服务器回环地址启动、且 SSH 恢复后，可这样建立网页隧道（在 Windows 仓库根目录执行）：

```powershell
ssh -i work/cloud/lab-ubuntu-dev/doorhandle_lab_ed25519 -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes -N -L 127.0.0.1:18088:127.0.0.1:8088 wml@10.22.0.145
```

连接成功且服务就绪后，浏览器访问 `http://127.0.0.1:18088/` 或 `http://127.0.0.1:18088/agent-ui/`。临时候选以本轮实际发放的地址和有效期为准。专用密钥文件在 Git 忽略目录，不提交、不共享私钥。

## 3. 账号、权限与目录先确认，再配置

### 账号与凭据

1. 优先沿用 Linux 账号 `wml`，先读取实际 UID/GID；不能照搬 ECS 的 UID、machine-id 或实例编号。
2. 复用已登记的项目专用 SSH 密钥；主机地址变化时仍与 Linux 本机显示的指纹核对，不关闭主机密钥校验。
3. 以后若启用 Jenkins，再通过 Jenkins Credentials 管理自动化凭据；代码只引用 credential ID。不得把密码、私钥、模型密钥或真实环境文件提交、归档或粘贴到文档。
4. Docker 权限需主机负责人批准。rootful Docker 的 socket 或 `docker` 组访问具有接近主机 root 的能力，专用目录和普通用户名称不能消除这一权限。不得使用 `chmod 666 /var/run/docker.sock` 或全局免密 sudo 解决报错。
5. 如果这台实验室设备不允许项目执行账号拥有所需 Docker 权限，先确定受支持的隔离执行环境；不能静默切换 rootless Docker 后继续套用原有 cgroup、挂载和恢复断言。

### 部署根目录与用途

Windows 保留现有源码、Jenkins 工作区和 D 盘原始报告，不搬动现有 Jenkins Home，不在 C 盘新增工具或下载目录。

以用户指定的 Linux 目录为项目根。隔离验收使用 `ci/<流水线运行编号>/`，不直接覆盖根目录，不把长期运行目录用于测试：

```text
/home/wml/xm/bpaper/lunwen3/
├─ ci/          # 每轮独立执行目录及可再生成物
├─ runtime/     # 长期单体发布目录；本轮测试不使用
├─ private/     # 私有配置、只读 Secret 挂载源
├─ models/      # 检测权重、配套源码清单，只读供 worker 使用
├─ backups/     # 数据恢复点，禁止纳入普通 CI 自动清理
├─ evidence/    # 本轮原始回执和迁移依据
└─ cache/       # 有明确配方、来源和容量边界的项目缓存
```

根目录由用户创建，子目录由流水线按需建立，预检先核对实际路径、所有者、执行账号的读写权限和所在分区。项目根目录与 Docker Root Dir 不一定在同一分区，分别核对容量；现有 Docker Root Dir 和项目以外的卷、镜像、研究数据保持原状。不擅自迁移全机 Docker 数据目录，也不修改现有 Conda `base` 环境。

### 4.3 外部服务与历史组件另列清楚

- **OSS**：图片、结果及相关对象仍依赖已配置的阿里云 OSS。迁换计算主机不会自动把桶和数据迁回来；默认保留已有地址与授权，不开放匿名读写，不擅自替换成 MinIO。
- **模型／embedding API**：沿用受控模型配置和密钥治理。验收保持既有零付费约束，不默认批量重新调用模型或重建全部 embedding；真实付费调用需明确授权。
- **Chroma**：只保留为历史读取／恢复来源。当前新运行时使用 Qdrant，不为“组件齐全”额外长期启动旧 Chroma；相关依赖包存在不等于需要一个常驻 Chroma 服务。
- **验收辅助服务**：受控模型、浏览器、MCP 测试进程及其他 fixture 只在所属验收阶段启动，按原资源表收尾；不能把它们全部转成长期开机服务。

## 5. 32 GiB 主机先采用核心栈，不同时叠加完整 Langfuse

当前 Compose 对后端、MySQL、业务 Redis、Kafka、Qdrant、Mem0、worker、Higress、MCP runner／egress、Prometheus 和 Alertmanager 声明的内存上限合计为 **14.5 GiB**，另需 Nginx、Docker、宿主系统及其他实验任务的空间。这是配置上限之和，不是实测峰值，也不是验收进程的完整预算。

Langfuse 五个长期服务的当前上限另计 **21.5 GiB**。两组直接相加为 **36 GiB**，超过该机报告的约 31 GiB 总内存，因此不推荐在这台机器上按当前完整配置同时常驻全部组件。

推荐配置是核心业务加按需指标监控；Langfuse 单独按功能需要和资源门安排。已有 `deploy/compose/compose.observability.smoke.yml` 将 Langfuse 五服务上限合计约束到 **5 GiB**，但它仅用于隔离、无真实业务流量的功能 smoke，不能冒充生产容量配置。若必需验收范围包含某项观测能力，仍须满足对应执行条件并保留真实证据，不能直接略过。

其他约束：

- 现有测试和运行阶段的 cgroup、OOM、磁盘保底及限额继续有效；不要因为机器有 28 线程就开启无界并发。主机原有实验占用必须进入实际准入。
- 一次只运行一条完整验收链；旧服务、测试环境、Langfuse 和构建临时物的并发需要统一核算，不能仅分别看每个容器上限。
- `/` 和 `/home` 的空闲量分别记账，不能相加后假定 Docker 卷可使用全部空间。先确认 Docker Root Dir，再确定新项目卷的位置。
- 沿用已有日志轮转与缓存预算，不为查看日志开多套观测服务，不复制所有历史 CI 工作区到新主机。
- 清理必须核实活动引用和静态来源依赖。共享工具原始安装者、恢复资料、审计输入及必要原始报告不按“重复文件”直接删除；不执行全局 `docker system prune`。

## 6. 后续若用 Jenkins，先适配目标准入

当前脚本校验阿里云 IMDS、固定 ECS 实例和 machine-id，并包含原路径、UID、镜像来源和维护证据合同。迁入普通 Ubuntu 后，删除这些检查或伪造 ECS 身份都不是可用方案。

| 适配项 | 启用实验室 Jenkins 验收前的要求 |
| --- | --- |
| 运行目标与身份 | 新增显式实验室 Linux 目标配置，绑定 SSH 主机公钥、实际 machine-id、执行 UID/GID、项目根目录和允许的传输方式；保留原 ECS 模式的默认合同 |
| 源码与制品 | 沿 `Jenkinsfile.ecs-monolith` 和现有脚本检出固定提交、跳测试构建、封存源码／JAR／镜像及实际输入，不用未提交工作区发布 |
| 私有路径 | 统一适配新的 CI、runtime、配置和模型目录，完成直接调用方、回收白名单、卷挂载及恢复路径，不只改一个环境变量 |
| 工具与缓存 | Linux 上的安装者和镜像来源要有真实的新主机证据；可以迁入经验证的不可变镜像输入，但不能复制旧 ECS PID、boot-id、owner 后声称它们在新机执行过 |
| 迁机首次切表 | 区分旧 ECS 源机、最终停写备份和新 Linux 目标；不能把现有同机切表流程仅换地址就当作跨机迁移完成 |
| 取消、断线及恢复 | 绑定原 attempt／进程／主机身份，先查原执行状态与收证，再决定续接或失败；断 SSH、控制器重启或主机停机不自动启动第二条相同验收 |
| 清理与证据 | 每轮标签、容器／目录归属、新旧主机证据分开，保留静态来源依赖与原始报告；只清明确拥有的临时资源 |

沿用当前 `java-cloud` 的业务源码。全部适配及必要回归整合后形成一个固定提交；旧 ECS 的局部结果不拼接成新主机验收通过。

发布门 `DOORHANDLE_COMPACT_RELEASE_READY`、演练门 `DOORHANDLE_COMPACT_REHEARSAL_READY` 继续默认关闭；新目标准入须绑定版本化配置、固定提交和实际验收证据，不能仅在 Jenkins 页面改参数绕过。

## 7. 数据先保全，再按现有迁移规则形成 29 表

1. **盘点并封存来源**：核实旧库当前数据、最后写入时间和可恢复的完整 131 表备份；保全上传资料、模型权重与匹配清单、Agent 工作空间、Mem0／Qdrant／历史 Chroma、网关配置、MCP 执行日志和模型主密钥。私有资料不进入 Git 或公开 Jenkins 归档。
2. **先做候选试迁**：在 Linux 独立拥有的源库副本与目标库上复用现有 31 步迁移、双恢复和读回验证。保留源／目标的真实身份，不把恢复出来的副本说成旧机现场业务库。
3. **明确 Redis 的数据性质**：已有 `cache:v2` 派生缓存可在新环境按原键协议和 TTL 重建；模型熔断 Hash 是协调状态，保留其配置版本、租约与失效规则。其他实际 key 先分类再决定处理，不声称整个 Redis 都可丢弃，不对旧库或全机执行 `FLUSHALL`。
4. **消息与向量不盲目重放**：Kafka 保留必要消息、消费位点及未完成／未知任务的对账依据，不默认回放历史归档；Mem0／Qdrant 校验集合、记录、向量配置和持久资料，不默认用重新调用模型来替代迁移。
5. **人工验收后才正式切换**：用户确认同一候选后，进入受控维护窗，冻结旧入口与写者，取得最终新鲜备份，重新迁移到正式 29 表目标并校验。候选试迁数据不能直接覆盖正式新数据；已物化的记忆／向量候选也必须核实来源新鲜度。
6. **防止双写与错误回退**：新 Linux 正式启写后，旧 ECS 写者保持停写。新库可能已有写入时保留新库，走同目标恢复或前向修复，不自动切回旧 131 表写者。旧库、SQL、报告及 #266/#117 等受保护恢复资料继续保留。

如果缺少可证明最新且完整的来源备份，由用户临时启动原 ECS 取数；流水线只调度已启动目标，不负责云端启停，也不查询账单或卡券。原机与保留资源的后续处置，在新机验收、正式读回和备份确认后由用户决定。

## 8. 全部适配完成后，统一验收

实施顺序：

1. **核实新测试目标**：确认 SSH 密钥登录、Docker 权限和版本、UID/GID、主机身份、磁盘位置及测试输入；核对原 #426 的残留状态，保全原件，不在新旧目标同时启动验收。
2. **集中完成开发整合**：运行约定、目标配置、身份校验、迁移接线、业务／中间件配置、依赖来源、取消恢复、清理和回归代码一起完成。
3. **本地跳测试构建并固定提交**：检查 SCM 自动触发，避免中途提交启动项目测试；部署必须绑定这一固定提交和对应制品。
4. **在 Linux 统一自动验收**：控制检查在同一完整 Python 执行中先完成；保留全量 Python、原生 MySQL、普通 Java、两套前端、真实 Redis、迁移／双恢复及全部规定运行／浏览器场景。真实 Redis 当前基线 25 项须实际运行；账号仍是 2 个检测人员、2 个主管，各 2 标签。正式容量压测继续按用户决定后置。
5. **交用户验收同一候选**：提供真实地址、账号说明、提交和有效期，检查实际页面与关键交互。由用户明确选择通过或反馈问题，不自动代替用户确认。
6. **验收后收尾**：安全清理本轮自有临时资源并保全原始证据。正式发布必须另有明确目标及授权；符合相同提交、输入、范围和制品条件的有效验收证据可复用，不因进入发布阶段重复验证。

失败时先收齐已知问题，集中修复调用方、配置和夹具，再按影响范围统一复测。检查资源与证据的实际条件发生变化时重新评估；不能以缩小范围、跳过失败或跨主机拼 PASS 宣称完成。

本轮完成条件是：新目标身份和权限有效，候选中间件健康，完整规定检查通过（含隔离候选 29 表迁移与读回），用户完成同一候选功能验收，证据及恢复点可用。正式库切换和旧写者停写属于另行批准的发布阶段。

## 9. 开工和验收前的检查项

- 用户／主机负责人确认：SSH 密钥登录和 Docker 执行权限；验收期间允许的资源占用与开机窗口。
- 只读查询：Docker 服务端版本、Compose 插件、Docker Root Dir、实际 UID/GID 和 SSH 主机公钥指纹。通过验明主机公钥的 SSH 通道登记机器身份。
- 实施负责人确认：旧机最新数据与恢复点是否完整可用，#426 原执行如何收尾，校园内网地址是否稳定。

可在 Linux 手动查询并提交非敏感输出：

```bash
ip -br -4 addr show scope global
id
project_root=/home/wml/xm/bpaper/lunwen3
stat -c 'owner=%U:%G mode=%a path=%n' "$project_root"
df -hT "$project_root"
if test -w "$project_root" && test -x "$project_root"; then echo '目录可写、可进入'; else echo '目录权限不足'; fi
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
docker compose version
sudo docker info --format 'Docker={{.ServerVersion}} cgroup={{.CgroupVersion}} 驱动={{.Driver}} 数据目录={{.DockerRootDir}}'
```

机器身份由实施时通过已验证的 SSH 通道读取并登记；不要求在公开文档粘贴密码、私钥或真实配置。若 SSH 主机公钥类型不同，核对实际使用的主机公钥，不自动生成或替换服务器密钥。
