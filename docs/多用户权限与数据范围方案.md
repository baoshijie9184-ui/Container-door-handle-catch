# 单企业多用户权限与数据范围方案

更新日期：2026-10-13；当前分支：`java`。沿用 Java 17、Spring Boot 3.2.4、Spring Security、MyBatis-Plus 3.5.5、MySQL 和 AgentScope Java 的模块化单体。

## 已确定的规则

一个系统、一个企业数据库支持多个账号登录。用户选择的业务范围为“员工看本人及分派任务，主管看全企业”。业务范围与账号私有资源分别判断。

| 资源 | 检测员工 | 检测主管 |
| --- | --- | --- |
| 检测任务、结果、追溯、质检队列 | 本人创建，或当前分派给本人 | 当前企业全部 |
| 检测统计、图表、记录列表 | 根据可访问任务计算 | 当前企业全部 |
| 任务原图、标注图、结果文件 | 必须关联可访问任务 | 必须关联企业任务 |
| 质检任务分配 | 无分配权限 | 业务入口可分配；Agent 提议需人工确认 |
| 私人聊天、运行日志、记忆、操作确认与确认审计 | 仅所属账号 | 仅所属账号，不因主管身份获得他人私人内容 |
| 模型、设备等公共参考目录 | 沿用现有查询权限 | 沿用现有管理权限 |

“可查看任务”不自动赋予所有业务写权限。写操作仍遵守角色、任务状态和人工确认规则。本次统一检测任务数据范围；员工与人员档案的绑定、部门范围及设备使用记录的个人权限尚未完整实现。

## 开源方法调查与取舍

多用户通常采用同一应用实例、独立身份、角色权限和数据库行过滤，不需要为每个员工部署一个服务。角色权限回答可执行哪些操作，数据范围回答可操作哪些记录。

| 参考 | 可借鉴的方法 | 与当前项目的关系 |
| --- | --- | --- |
| [ruoyi-vue-pro](https://github.com/YunaiV/ruoyi-vue-pro) | 用户、角色、部门、数据权限；支持 Spring Security、MyBatis-Plus、Vue/Element | 技术路线接近，适合后续扩展动态 RBAC 和部门范围；其 JDK 17 分支的 Spring Boot 版本与当前项目不同，需按版本适配 |
| [RuoYi-Vue-Plus](https://github.com/dromara/RuoYi-Vue-Plus) | 数据权限与多租户后台设计 | 使用 Sa-Token，作为设计参考；当前继续使用 Spring Security |
| [MyBatis-Plus 数据权限插件](https://baomidou.com/plugins/data-permission/) | 拦截 SQL，依据自定义规则添加权限条件 | 未来复杂联表可评估；现有 JDBC 查询也必须显式授权，单独安装 MyBatis 插件不能覆盖这些接口 |

两个 RuoYi 项目均已核对 MIT 许可证：[Pro LICENSE](https://github.com/YunaiV/ruoyi-vue-pro/blob/master/LICENSE)、[Plus LICENSE](https://github.com/dromara/RuoYi-Vue-Plus/blob/6.X/LICENSE)。本次参考权限设计，没有复制其源码或引入新框架依赖；如后续复制源码，应保留版权及许可声明。仓库提供分支与提交历史，但本次未做长期维护质量或生产性能评估。

## 当前实施

此前业务页面允许所有登录用户访问全部检测任务，而员工 Agent 只查询本人创建的任务。统一后，由检测模块 `DetectionTaskAccessPolicy` 提供相同规则：

```sql
-- 员工：必须与其他筛选条件以 AND 连接，并保留括号
WHERE (created_by = :currentUsername OR assignee = :currentUsername)
  AND ...业务筛选条件...
```

身份来自 Spring Security 或服务端生成的 `AgentActor`，不接受前端、模型传入的当前用户或角色。主管与旧管理员角色使用企业范围。分页、总数和聚合在数据库中过滤，不能先读出所有记录再只过滤列表。

覆盖路径：检测任务列表、详情、结果、进度、追溯、质检报告与队列、缺陷图库、批次与工单追溯；旧检测记录接口；直接检测数据列表与详情；首页检测计数、趋势、分布、地区、模型、处置和待办统计；旧统计接口；Agent 检测查询与统计；OSS 预览授权；本地检测文件与目录列表。

首页原先使用全局固定缓存键，可能将主管统计返回给员工。本次取消这些检测统计的共享缓存，直接按当前身份查询。后续若恢复缓存，必须包含用户、权限版本与范围，并在分派变动后失效。

本地文件通过基础设施权限端口调用检测模块判断关联任务；移除绕过文件控制器的上传目录静态映射。新本地检测目录加入随机后缀，避免不同用户在同一秒检测时复用目录。不存在有效任务关联的旧本地文件不授予读取权限。历史上已混用同一目录的任务仍需要人工核对和迁移；本次不移动历史文件。已发出的 OSS 签名链接在有效期内不会因重新分派立即失效，严要求场景需改为代理读取或缩短链接有效期。

重新分派后，原责任人若不是任务创建者，下一次服务端查询即失去访问权；创建者仍可访问本人任务。后台检测回调保留专用系统查询路径，不依赖请求线程用户身份。

## 单体阶段的边界与后续

当前只有一家公司，尚未实现 `tenant_id` 企业隔离，也没有把任务用户名关系改为稳定的用户 ID。主管“全企业”以当前部署仅包含本公司数据为前提。账号、员工、部门稳定 ID 关联及主管管理页面已完成，见 [账号员工部门关联](账号员工部门关联.md)；关联不扩大任务范围。后续迁移 `creator_user_id` 与 `assignee_user_id`，再增加部门与可配置权限；确实接入第二家公司时，才统一引入企业字段、唯一约束、索引、缓存和工作区隔离。

旧方案中的“所有登录用户共享业务和聊天、相同能力”已被本规则替代。公共检测记录的独立审批发布方案是后续能力；没有审批发布实现前，不以公共记录为由扩大员工任务读取范围。

本次验证包括账号范围、跨账号任务拒绝、图片授权、新旧列表与统计一致性、Agent SQL 和重新分派后权限撤销。测试样本使用 `scope-fixture-*` 标记，保留供复核，不修改原业务任务。显式本机测试开关为 `detection.scope.local.mysql=true`，报告位于 `work/task-scope-local-mysql.json`。这不是并发容量或多企业隔离验收。

真实 MySQL 和后端联调已通过：两名员工与主管的任务总数、旧记录总数和首页检测计数分别与对应数据库范围一致；所有检测图表查询成功；他人任务及旧记录详情拒绝访问；分派员工可以读取关联图片，未分派员工无法通过四个文件入口或标注目录列表读取；重新分派后，原责任人的任务、Agent 查询和图片访问均被拒绝。本地文件响应使用 `Cache-Control: no-store`，避免跨账号复用浏览器缓存。全量 Maven verify 与最终打包通过，浏览器另验证三个账号的实际检测记录页面，报告为 `work/task-scope-browser.json`。

页面验证同时修复了旧检测历史搜索框未将关键词传入查询参数的问题；关键词搜索与其他筛选均在后端权限范围内执行。
